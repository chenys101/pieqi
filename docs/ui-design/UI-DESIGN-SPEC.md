# Pieqi UI Design Specification

> 版本 v1.1 · 三页（Dashboard / Session Timeline / Settings）
> 定位：**Linear 的克制 + GitHub 的信息密度 + AI Agent Console 的实时感**
> 主题策略：**浅色优先，双主题对等**（浅色不再是深色的机械反转，独立调校）；
> 用户侧为三态 `跟随系统 / 浅色 / 深色`，**默认跟随系统** —— 详见 §5.5

---

## 1. 设计目标

Pieqi 不是一个"显示 Agent 输出的面板"，而是围绕 Agent Task 的 **Observe → Verify → Control → Intervene** 反馈层。
因此 UI 的成功标准不是"好看"，而是三个可度量的行为指标：

| 指标 | 定义 | 目标 |
|---|---|---|
| **介入时延** | 任务进入 waiting_input → 用户完成决策的时间 | 移动端 < 15s，无需滚动 |
| **验证成本** | 用户判断"改得对不对"所需的点击数 | ≤ 2 次点击看到 Diff + Preview |
| **误判率** | 用户错误地把未完成/已失败任务当作已完成 | 状态表达零歧义 |

### 1.1 五条设计原则

1. **State over Content** — 用户第一眼要看的是"要不要我管"，不是"Agent 说了什么"。所有列表按**介入优先级**排序，而非时间或状态枚举。
2. **One Screen, One Decision** — 决策类操作必须在单屏内完成，主行动按钮常驻，禁止藏在 Drawer 里。
3. **Progressive Disclosure** — Timeline 默认只呈现主干（用户指令 / Agent 结论 / 变更摘要 / 决策点），thinking 与工具 IO 折叠收纳。
4. **Reversible by Default** — Rewind 是 Pieqi 的核心差异能力，必须是显性、低风险、有二次确认的（内联确认，绝不用原生 `confirm()`）。
5. **Quiet by Default** — 实时不等于躁动。流式更新用微弱的运动提示呼吸感，禁用大面积色块跳动。

## 2. 信息架构

```
侧边栏（桌面）                        底栏（移动）
 仪表盘 ──► Dashboard               首页 ──► Dashboard
 新建任务（主操作，范围外）           任务 ──► 任务浏览器（移动端专用页）
 任务列表 ──▼ 分组，不是页面          设置 ──► 设置（全局偏好 · 机器人）
   └ 项目行（**全部项目，默认收起**）
       └ 点击项目 → 展开该项目任务（**按最近更新排序**）──► 主区任务详情
 设置 ● 连接正常 ──► 设置（唯一一处连接状态）

主区（Main）承担三件事，同屏互斥：
 ① Dashboard：待审批 + 本周概览
 ② Session Timeline：任务详情 —— Turn 分组时间线（我说的 → Agent 做的 → 改了什么）
                     右栏「变更反馈」**默认收起**为 46px 竖向贴边条，点击才展开 420px
                     底部干预输入（支持 /skill 自动补全）
 ③ Settings：跨任务 / 跨项目的全局偏好（见 §5.4）

统一的决策卡 ── ① 仪表盘「待审批」组   ② Session 内联决策
```

> 决策卡的复用场景曾写作"① Dashboard 焦点区 ② Session 内联 ③ 审批中心"。
> 现已**无独立审批中心** —— 它与「待决策」状态语义重复，会成为第二个待办容器。
> 收敛为两处：**仪表盘的待审批组 + Session 内联决策**，卡片本身则有三种风险变体。

> **主区不是「任务列表页」。** 任务浏览是**导航行为**，归属侧栏任务树；
> 主区只在「你选中了某个任务」时才切换到详情。曾把任务列表做成主区页面，
> 结果是「浏览」和「阅读」抢同一块屏幕 —— 浏览要广度，阅读要深度，两者诉求相反。

**关键架构改动**：桌面端把「变更反馈」从 Drawer 提升为**右栏常驻面板** ——
但**默认收起**，不是默认展开。理由见 5.2。

### 2.1 导航映射与"范围外"处理

原型主区实现三页（Dashboard / Session / Settings），侧栏任务树与底栏承载完整 IA，必须避免**死链**。

**核心原则：项目 = 空间 = 任务，是「分组维度」与「组内条目」的关系。**

| 位置 | 项 | 行为 | 高亮依据 |
|---|---|---|---|
| 侧边栏 | 仪表盘 | → Dashboard（待审批 + 本周概览） | `data-nav="dashboard"` |
| 侧边栏 | 新建任务 | 范围外 → Toast 说明 | 主操作按钮 |
| 侧边栏 | 任务列表 | **分组头**（默认展开）→ 其下直接列出全部项目，不走页面跳转 | 无 `data-nav`，永不作为导航高亮 |
| 侧边栏 | ├ 项目行 | 点开/收起 → 展开该项目任务 | `aria-expanded` |
| 侧边栏 | └ 任务行 | → **主区** Session 详情 | `.sb-task.is-active` |
| 侧边栏 | 设置 | → Settings 页；行尾带连接状态（唯一一处） | `data-nav="settings"` |
| 底栏（移动） | 首页 | → Dashboard | `data-goto` |
| 底栏（移动） | 任务 | → 任务浏览器页（移动端专用，内容同上） | `data-goto` |
| 底栏（移动） | 设置 | → Settings 页（同构） | `data-goto` |

**侧边栏 3 个导航项 + 1 个分组，底栏 3 项。** 桌面多一个「新建任务」主操作（横向空间充足）。

**仪表盘承载审批。** 待审批不是独立目的地而是仪表盘的核心内容 ——
「审批」作为导航项会与「待决策」状态重复含义。Agent 请求权限时，
卡片实时出现在仪表盘焦点区的「待审批」组，处理完该组自动收起。
待审批数量以徽章挂在「仪表盘」项上（`badge-mini`），而非单独一列。

**底栏约束**：每一项都必须是顶层目的地（页面切换）。不允许某一项触发弹层 ——
同类外观必须给出同类行为。选择器性质的入口放在内容区，不放底栏。

> **「任务列表」这个入口的演化**（完整记录，避免再摇摆）：
> ① 一版把它直接接到 Session 页 → **层级塌陷**：期望列表却被丢进实例。
> ② 删除它，理由是"仪表盘本身就是任务列表" → 仪表盘被迫同时承担
> **行动面**与**历史档案**，任务一多就无限拉长（~2500px）。
> ③ 恢复为 Tasks 集合页，同时侧边栏保留「项目树」 → 两份实现，重复。
> ④ 删掉侧边栏树，只留 Tasks 集合页，Dashboard 加「本周概览」。
> ⑤ **终态（当前）**：**任务列表从"页面"降级为"侧栏分组"**，其下直接列出所有项目，
> 项目展开才出任务；主区归还给任务详情。详见 §6.1。

**实现约束**：`data-nav`（身份/高亮）与 `data-goto`（跳转目标）必须分离。
初版二者合一导致「仪表盘 / 任务 / Agent」三个按钮同时指向 `dashboard`，
于是**三个按钮同时高亮**且点击无变化 —— 用户感知就是"点不动"。
任务树的选中态用独立类 `.sb-task.is-active`，且**只在会话页生效** ——
树表达的是"我现在在哪"，不是"我看过什么"。

**进入实例时必须同步实例身份**：从任务树的任一任务行进入 Session，
要同时更新标题（`#sessionTaskName`）与项目名（`#sessionProjectName`），
否则点哪个任务都看见同一条内容，原型就失去说服力。
统一由 `taskInfo(el)` 解析（`data-task` / `data-proj` 优先，回退到可见文本），
使三种入口（任务行 / 焦点区卡 / 会话内跳转）行为一致。

**范围外项不要用 `disabled`**：置灰会被读成"功能坏了"。
正确做法是保持可点击 + 中性 Toast（新增 `.toast.info`，accent 色，非绿勾），
明确告知"不在本次原型范围内"。这是 Prototype Honesty 原则：宁可说明，不可装死。

## 3. 设计令牌（Foundation）

### 3.1 色彩 — 浅色主题（默认）

三层表面采用**非纯白**策略降低眩光，卡片用纯白浮起，靠阴影而非边框建立层次。

| Token | Hex | 用途 | 对比度 |
|---|---|---|---|
| `--canvas` | `#F6F7F9` | 页面底色 | — |
| `--surface` | `#FFFFFF` | 卡片 / 弹层 | — |
| `--surface-subtle` | `#F8F9FB` | 次级区块、输入框底 | — |
| `--surface-muted` | `#F0F2F5` | 禁用态、代码块底 | — |
| `--surface-inset` | `#E9ECF1` | 凹槽（Diff 行背景） | — |
| `--border-subtle` | `#EDEFF3` | 极弱分隔 | — |
| `--border` | `#E1E4EA` | 默认边框 | — |
| `--border-strong` | `#CDD2DB` | 悬停 / 聚焦边框 | — |
| `--text-primary` | `#15171C` | 正文标题 | 15.8:1 ✓ AAA |
| `--text-secondary` | `#4A5160` | 次级信息 | 7.8:1 ✓ AAA |
| `--text-tertiary` | `#6B7280` | 时间戳、辅助说明 | 4.8:1 ✓ AA |
| `--text-disabled` | `#9BA2AF` | 禁用（豁免对比要求） | 2.6:1 |

**强调与语义色**（语义色同时在白底与各自浅色底上通过 AA）

| Token | Hex | 浅底 bg | 用途 |
|---|---|---|---|
| `--accent` | `#6E41CD` | `#F4EFFE` | 主行动、选中态 |
| `--accent-hover` | `#5E34B8` | — | 悬停 |
| `--accent-active` | `#512C9E` | — | 按下 |
| `--accent-ring` | `#6E41CD33` | — | 焦点环 |
| `--success` | `#1A7F45` | `#E7F6EC` | 运行中 / 检查通过 / 新增行 |
| `--warning` | `#B45309` | `#FEF4E6` | 待决策 / 高风险操作 |
| `--danger` | `#B42318` | `#FEECEA` | 失败 / 破坏性操作 / 删除行 |
| `--info` | `#175CD3` | `#E8F1FE` | 排队中 / 提示 |

> **为什么不用亮紫 `#8857f5`**：该色在白底对比度仅 4.4:1，按钮白字不达 AA。`#6E41CD` 为 6.4:1。
> **为什么边框变浅**：浅色主题下，层次应由阴影承担。现有主题的 border `#D0D4D8` 在浅底上过重，让界面显脏。

|---|---|---|---|---|
| `display` | 30 / 1.875 | 1.25 | 650 | 空态主标题 |
| `title-1` | 24 / 1.5 | 1.3 | 650 | 页面标题 |
| `title-2` | 18 / 1.125 | 1.35 | 600 | 区块标题 |

### 3.4 间距与几何

4px 基准网格：`0 · 2 · 4 · 6 · 8 · 12 · 16 · 20 · 24 · 32 · 40 · 48`

| Token | 值 | 用途 |
|---|---|---|
| `--radius-xs` | 4px | 徽章、代码内联 |
| `--radius-sm` | 6px | 按钮、输入框、tool 行 |
| `--radius-md` | 8px | **卡片默认** |
| `--radius-lg` | 12px | 大卡片、模态框 |
| `--radius-xl` | 16px | Drawer、浮层 |
| `--radius-full` | 9999px | 状态点、头像、chip |

**触控靶**：所有可点元素最小命中区 **44×44px**（视觉尺寸可小于此值，用伪元素扩展命中）。

### 3.5 阴影（浅色专用）

深色主题下阴影置为 `none`，改用 `--border` 建立层次。

```css
--shadow-xs: 0 1px 2px rgba(16, 18, 27, .04);
--shadow-sm: 0 1px 3px rgba(16, 18, 27, .06), 0 1px 2px rgba(16, 18, 27, .04);
--shadow-md: 0 4px 8px -2px rgba(16, 18, 27, .08), 0 2px 4px -2px rgba(16, 18, 27, .04);
--shadow-lg: 0 12px 16px -4px rgba(16, 18, 27, .08), 0 4px 6px -2px rgba(16, 18, 27, .03);
--shadow-focus: 0 0 0 3px var(--accent-ring);
```

### 3.6 动效

| Token | 值 | 用途 |
|---|---|---|
| `--ease-out` | `cubic-bezier(.16, 1, .3, 1)` | 入场、展开 |
| `--ease-standard` | `cubic-bezier(.2, 0, 0, 1)` | 常规过渡 |
| `--dur-instant` | 80ms | hover / active |
| `--dur-fast` | 150ms | 折叠、徽章变化 |
| `--dur-base` | 220ms | Drawer / Modal |
| `--dur-slow` | 320ms | 页面级切换 |

- **流式呼吸**：Agent 运行中状态点用 2s ease-in-out 无限`opacity .45→1` + `scale .92→1`，**禁止位移**。
- **事件入场**：新事件卡片 `opacity 0→1` + `translateY(4px→0)`，160ms，仅首次渲染触发（重连回填不触发动画）。
- **尊重系统偏好**：`@media (prefers-reduced-motion: reduce)` 下所有动画降级为 0ms 直接切换。

## 4. 组件库规格（补齐至 26 件）

现有 9 件：Button、Badge、Card、Drawer、EmptyState、Modal、Spinner、ToastHost、StatusBadge。
需补齐 16 件，并统一现有件的规格；另有 1 件（`QRScan`）是随 5.4.2 的扫码流程新增的 ——
它不是"补齐"出来的，是流程带来的新件。

### 4.1 Button

| 尺寸 | 高度 | padding | 字号 | 圆角 |
|---|---|---|---|---|
| `sm` | 28px | 0 10px | 13px | 6px |
| `md` | 36px | 0 14px | 14px | 6px |
| `lg` | 44px | 0 18px | 15px | 8px |

| 变体 | 默认 | 悬停 | 说明 |
|---|---|---|---|
| `primary` | `bg-accent text-white` | `bg-accent-hover` | **每屏最多一个** |
| `secondary` | `bg-surface border-border text-primary` | `bg-surface-subtle border-border-strong` | 常规次要动作 |
| `ghost` | 透明 + `text-secondary` | `bg-surface-muted` | 工具栏 |
| `danger` | `bg-danger text-white` | 加深 8% | 删除、拒绝 |
| `warning` | `bg-warning-bg border-warning/30 text-warning` | — | 高风险确认 |

状态：`loading`（内联 spinner + 保留原宽度防抖动）、`disabled`（opacity .5，pointer-events none）、`focus-visible`（3px accent ring）。

### 4.2 StatusSystem（状态表达统一）

这是全站最关键的一致性约束——**同一个状态在任何地方必须长一样**。

| 状态 | 点颜色 | 文案 | 徽章底 | 是否脉动 |
|---|---|---|---|---|
| `pending` | `#8A91A0` 空心 | 排队中 | neutral | ✗ |
| `running` | success | 运行中 | success-bg | ✓ 呼吸 |
| `waiting_input` | warning | 待决策 | warning-bg | ✓ 呼吸 |
| `completed` | success 实心 | 已完成 | success-bg | ✗ |
| `failed` | danger | 失败 | danger-bg | ✗ |
| `cancelled` | tertiary 空心 | 已取消 | neutral | ✗ |

**Spec**：状态点 6×6px、圆角 full、容器 8×8px 保证对齐；徽章 = 12px caption + 圆角 xs + padding `2px 8px` + `[色]-bg` 底 + `[色]` 文字；徽章可选前缀图标。

### 4.3 ApprovalCard（★ 核心组件，三处复用）

统一 `ApprovalCard` / `ApprovalBanner` 的重复实现，单一 Props：`{ request, context: 'dashboard' | 'session' | 'center', compact? }`。

**布局（自上而下）**

```
┌────────────────────────────────────────────┐
│ ⚠ [风险等级 chip]                 12s 前   │  ← 头部：风险标 + 相对时间
│                                            │
│ Claude Code 想要执行一条 Shell 命令        │  ← title-3，一句话讲清"谁要干什么"
│                                            │
│ ┌──────────────────────────────────────┐  │
│ │ $ rm -rf ./node_modules/.cache       │  │  ← mono 13px，surface-inset 底
│ └──────────────────────────────────────┘  │
│                                            │
│ ▸ 查看将影响的 3 个文件                     │  ← 前瞻 Diff，Accordion 展开
│                                            │
│ [ 拒绝 ]  [ 仅此一次 ]  [ 始终允许 ]        │  ← sm @ desktop / lg @ mobile
└────────────────────────────────────────────┘
```

**风险分级**（依据 tool 类型 + 参数模式匹配）

| 等级 | 判定 | Chip | 边框 | 主按钮 |
|---|---|---|---|---|
| `L0 只读` | Read / Glob / Grep / LS | 中性 | border-subtle | primary 蓝 |
| `L1 写入` | Edit / Write / Notebook | 信息蓝 | info/25 | primary |
| `L2 执行` | Bash 非破坏性 | 橙 | warning/30 | warning |
| `L3 破坏` | `rm -rf` / `git push -f` / `DROP` / `chmod 777` | 红 | danger/35 | danger |

- `L3` 额外要求 **显式二次确认**（内联危险确认条，非原生弹窗）。
- 移动端：操作栏 `position: sticky; bottom: 0`，按钮 `lg` 44px，全宽排布（拒绝 / 允许一次 2:3 分栏）。

### 4.4 其余待补组件

| 组件 | 关键规格 |
|---|---|
| `Input` / `Textarea` | h 36px，border + `--radius-sm`，focus 时 border-accent + 3px ring；error 态 border-danger + 下方 12px caption |
| `Select` | 复用 Input 外壳，chevron 右侧 12px，菜单弹层 shadow-lg + radius-md |
| `Switch` | **状态在 `aria-checked` 上，视觉全由属性选择器驱动**（不额外维护 class，避免两份状态漂移）。轨道 38×22，knob 16px 带 `--border-strong` 描边（浅色下白 knob 落在 `surface-muted` 上需要描边才可见）；on 态轨道填 accent；`disabled` 与"无权修改"必须视觉可分 |

| `Modal` | 遮罩用 `--overlay` token，**不加模糊**（弹层是操作面，背后那张卡是这次操作的落点）；面板 radius-lg；展开时 `visibility` 立即可见、收起时延迟；打开后聚焦容器（`tabindex="-1"`）、Esc 关闭、焦点陷阱 + 关闭后焦点归还触发元素；移动端降级底部 Sheet（见 5.4.2）；页脚左侧可挂**低强调次要入口**（`.dlg-alt`，`margin-right: auto` + 无边框），用于"主路径走不通"的旁门 —— 它必须在主路径失效的那几个状态（生成中 / 已失效）里依然可见 |

| `EmptyState` | 图标 40px + title-3 + body-sm 说明 + 1 个 primary 行动；**禁止 emoji 充当图标** |

### 5.1 Dashboard — 从"状态陈列"改为"待办清单"

**问题**：早期版本用 4 个等权统计卡 + 按状态机械分组的两个列表 + 运行中 + 最近完成，
用户需要自己判断"现在该干什么"，且列表随历史无限增长。

**当前结构**（只有两块，规则见 §6.2）

   │ [查看会话][拒绝][我已知风险，执行]│ └───────────────┘ └──────────────┘

### 5.2 Session Timeline — 以 Turn 重构

**问题**：事件扁平流水，缺少"轮次"概念，用户无法把"我说的"和"Agent 改的"对应起来；变更反馈被塞在 Drawer 里。

**桌面布局**：`Grid 1fr 420px`，左 Timeline / 右 Feedback，中间 1px divider，均可独立滚动。
右列宽度由 `grid-template-columns` 驱动，收起时为 `1fr 46px` —— 见 5.2。

**Timeline 结构**

```
◀ 返回   修复订单创建时库存扣减…   [● 运行中]  ⋯ [中止]
         #a3f2 · oms-service · 12 分钟前

─── Turn 1 ───────────────────────────────────
  [右气泡] 帮我修复订单创建的库存扣减问题
      ⋮ 「思考 14 秒」▸ 折叠
      ⋮ Read  order/service.ts
      ⋮ Grep  "deductStock"
      ⋮ Edit  order/service.ts            +12 −4
      ⋮ Bash  npm test -- order            1.8s ✓
  [Agent] 我定位到库存扣减在事务外执行…
  ┌ 本轮变更 +3 文件 / +42 −18 ─── [查看 Diff] ─┐

─── Turn 2 ───────────────────────────────────
  [右气泡] 顺便补上单元测试
      ⋮ ⋯ 进行中
  ⏵ thinking…                      ← 呼吸点 + 微动省略号
```

**规则**
- **Thinking 默认折叠**为一枚 chip：`「思考 14 秒」`，点击展开；内容区最大高度 240px 内滚。
- **Tool Call** 折叠为单行：`[图标] ToolName  目标概要   耗时 状态`。点击展开入参 JSON 与结果，展开区 `surface-inset` 底 + mono 13px，最大高 320px 内滚。
- **Tool Result** 不再独立成卡——归属到对应 Tool Call 的展开区，解决"工具与结果分离"的割裂感。
- **Turn 尾部的变更摘要卡**是本轮唯一的 Verify 入口，点击联动右栏 Feedback 定位到该 Turn ——
  **收起态下必须先自动展开再切 Tab**，否则点了没反应，退化成隐性死链。
- **用户消息右对齐气泡**（accent-bg 浅色 + radius-lg + 右下角收窄 4px），Agent 消息左对齐无气泡（正文直排，减少视觉噪音）。
- 运行中且暂无事件时显示 `thinking indicator`，避免"看起来卡住了"。
- 虚拟滚动：内存保留最近 1000 条，超出部分按需从服务端分页加载。

**右栏「变更反馈」**（右栏常驻面板，替代 Drawer；**默认收起**，见 5.2.1）

```
┌── ProgressTabs ─ 概览 · 变更 · 检查 · 预览 ──┐
│                                                │
│ [概览]  TaskOutcomeCard                        │
│   完成度 / 文件数 / 增删 / 检查 / 回退次数     │
│                                                │
│ [变更]  Turn 列表 → FileChange → Diff          │
│   ● modify  src/order/service.ts  +12 −4  ▸   │
│   ● create  src/order/service.test.ts +30     │
│   底部：[ 回退到此轮之前 ]                     │
│                                                │
│ [检查]  ChecksPanel：单测 ✓ 1.8s / Lint ✓     │
│                                                │
│ [预览]  PreviewSection：启动 / 截图 / 外链     │
└────────────────────────────────────────────────┘
```

**回退（Rewind）交互重构** — 移除原生 `confirm()`：
点击「回退到此轮之前」→ 按钮原地变为内联确认条 `将丢弃 3 个文件的变更，确定？ [取消] [确认回退]`，3s 无操作自动收起。确认后按钮进入 loading → 成功 toast + Timeline 追加一条 Rewind 事件卡。

**移动端**：单列，底部 SegmentedControl 切换 `时间线 / 变更反馈`；决策卡与输入栏 sticky 吸底。

#### 5.2.1 变更反馈：默认收起为贴边条

「常驻右栏」曾经等于「默认展开」，这留了个隐患：**420px 是永久开销，不管你这会儿看不看**。
任务详情的主线是**读时间线**（我说的 → Agent 做的），反馈面板是**按需查看**的辅助面。
默认展开等于让辅助面先扣掉时间线 30% 的宽度，每行正文都被压短。

| 状态 | 表现 |
|---|---|
| 默认（收起） | 右边缘 46px 竖向贴边条：左向箭头 `‹` + 竖排「变更反馈」+ 变更文件数徽章 |
| 点击贴边条 | 展开为 420px 完整面板（Tabs 概览/变更/检查/预览），贴边条隐藏 |
| 点面板头部「收起」 | 回到 46px 贴边条 |

**收起不是"藏功能"**：贴边条本身就是展开入口，且带变更文件数 —— 用户不展开也知道
「有没有值得看的东西」。这是判断某结构能否默认收起的标准：
**收起态必须自己携带"要不要展开"的判据**，否则就变成了纯隐藏。

三条实现约束：

- **宽度由 `grid-template-columns` 驱动**（`1fr 420px` ↔ `1fr 46px`），展开/收起只切 class，
  动画交给浏览器排版；不写内联宽度、不测量像素。
- **收起态不丢状态**：标记存在 `fbCollapsed`，切页、切视口都保持。用户主动点开才展开，
  否则每次进详情都被"重置成展开"，等于没有默认收起。
- **移动端不套用收起态**。移动端反馈是**整屏**（顶部分段切换 `时间线 / 变更反馈`），
  没有"收起"这个概念 —— 所以：(a) 移动端强制展开面板（否则桌面收起会让手机端打不开反馈）；
  (b) 移动端隐藏贴边条与「收起」按钮 —— 那里没有可收起的目标，留着就是**点了没反应的死控件**。

> **箭头方向必须与动效方向一致。** 面板从右边缘**向左**拉出，贴边条箭头就应指向左 `‹`；
> 写成 `›` 会被读成"再往右推"，与点击后的实际动效相反。


### 5.3 Approval — 一处定义，多处复用

**无独立审批页。** 审批卡统一出现在**仪表盘焦点区的「待审批」组**（`/`）：

- 按风险降序排列（L3 破坏性 → L2 执行 → L1 写入），同风险按时间升序；
- L3 必须内联二次确认（详见 §5.4）；处理完卡片消解 + Toast 反馈；
- 全部处理完时该组整体收起，显示空态 `✓ 没有需要你处理的事项`（占据一行，不留白空缺）；
- 数量以徽章挂在侧边栏「仪表盘」项上 —— **待决策就是仪表盘的含义本身**。

原 `/approvals` 页的内容结构（此前的独立页面方案，已废弃）：

```
待决策（3）─────────────────────────────
 ┌ L3 破坏性 ──────────────────────────┐
 │ ⚠ 高风险  ·  rm -rf ./dist · 2 分钟前│
 │ Claude Code 想要清理构建产物         │
 │ [拒绝] [查看 Diff] [仅此一次]        │
 └─────────────────────────────────────┘
 ┌ L1 写入 ────────────────────────────┐
 │ ✎ 写入  ·  src/api/order.ts         │
 │ …
 └─────────────────────────────────────┘

已处理（今日 8）─────────── [展开]
 列表项：时间 · 动作 · 结果徽章（允许/拒绝）
```

- **默认按风险降序 + 时间升序**排序：高风险在前，避免用户误批危险操作后再批安全操作形成惯性；同风险内先到先处理。
- `L3` 卡片主按钮默认禁用 400ms，防止连点形成肌肉记忆误批。
- 空态：`✓ 全部处理完毕` + 说明"Agent 请求权限时会出现在这里"。
- 批量处理仅在同 `taskId` 且同风险等级时提供「全部允许一次」。

### 5.4 Settings — 只放"全局偏好"

设置是最容易变成垃圾桶的页面，因为它**没有内容模型**：前三个目的地都能从数据推导
（仪表盘=待审批，任务列表=项目/任务，详情=Turn），只有设置推导不出来。
所以先定裁决规则，再画页面：

> **设置只放「跨任务、跨项目、跨 agent 的全局偏好」。
> 属于某个对象的配置，就地设置。**

这条判据既是"该放什么"的答案，也是"什么不该放"的否决依据：

| 配置 | 归属 | 为什么 |
|---|---|---|
| agent 权限模式 | **会话详情** | 属于这个任务，换任务就该变 |
| 项目默认 agent / worktree | **项目行** | 属于这个项目，换项目就该变 |
| IM 绑定（机器人 × IM 身份） | **设置** | 全局；绑定单位是**机器人**而非渠道 —— 见 5.4.1 |
| 审批自动放行阈值 | **设置** | 全局，唯一能减少点击次数的开关 |
| 主题 / 语言 / 时区 | **设置** | 纯全局偏好 |

**分组与顺序**（顺序是刻意的，见下）：

| # | 组 | 内容 |
|---|---|---|
| 1 | 审批与自动化 | L0/L1 自动放行开关、L2/L3 锁定说明、免打扰时段 |
| 2 | 连接与账号 | 实时连接（状态 + 延迟 + 重连）、**IM 机器人**（列表 + 一键创建）、工作区路径 |
| 3 | 外观与偏好 | 主题三态、语言、时区、减弱动效 |
| 4 | 数据与关于 | 事件保留上限、诊断日志导出、版本 |

> **排序依据是"能减少你多少负担"，不是"有多无害"。** 惯例把「外观/通用」放最上，
> 那是在给不痛不痒的偏好排序；这个产品里最值钱的一组是**审批与自动化** ——
> 它直接决定你要被通知多少次。把最有价值的放最上。

**布局**：单列分组卡，`max-w-[760px]` 左对齐，无二级导航。
只有 4 组、内容短，二级导航会为几个锚点多占一列宽度，用户仍要滚动。

**控件约定**：
- 开关用 `role="switch"` + `aria-checked`，**视觉全由属性选择器驱动**，不额外维护 class ——
  避免"状态在 class 上、语义在 aria 上"两份状态漂移。
- **能力标记用独立类（`.cap-tag`），不复用状态徽章。** 「隧道 / API」是**权限**不是**状态**，
  借 `.badge.wait` 会把两套词汇混在一起；颜色上取 warning 槽位，表达"这是一项需要留意的特权"。
- **不可配置项做成"硬边界"而不是可配项**：L2/L3 显示为锁定行（`is-locked` 底 + `disabled`），
  不让用户把自己配进坑里。降级项（无权修改）与不可配置项在视觉上必须区分。

> **已移除「通知与推送」整组**（曾是第 2 组）：「事件 × 渠道」的逐条配置（需要审批 / 任务失败 /
> 任务完成 / 每日摘要 × 飞书·企微·微信）对当前阶段是**过度设计** —— 渠道本来就由绑定的机器人决定，
> 再让人逐事件选一遍渠道，等于把同一个决定拆成 12 个。移除后整组渠道 chip 的样式、
> DOM 与 JS 一并清掉（`chip-tg` / `set-chans` 已进禁止回归项），避免留下死代码。
> 免打扰时段保留在「审批与自动化」：它管的是**要不要打断你**，与自动放行是同一件事的两面。

#### 5.4.1 IM 绑定 = 机器人，不是渠道

绑定的单位是**机器人**：一台机器人对应一个 IM 身份（当前为 `飞书 · 管理员`）。

> **「机器人」是唯一层级 —— 不再有"智能体"这个中间名。**
> 两者曾经并存，但它们指同一件事（一个 IM 身份）。两套名字描述同一个东西，
> 用户只会花时间去猜哪个更大 —— 而这个问题的答案是"没有区别"，猜的过程纯属浪费。
> 收敛后的模型只有两层：**渠道（飞书 / 企微 / 微信）→ 机器人**。
> 用户可见文案里再出现"智能体"即视为回归（校验脚本已拦截；注释不计，
> 那里提它是为了说明"为什么不用它"）。

**管理员位的两种状态**（原型当前展示的是**未配置态** —— 那是首次使用的真实样子，
也是「一键创建」唯一该出现的位置）：

| 状态 | 状态点 | 标记 | 动作 | 副标题 |
|---|---|---|---|---|
| **未配置**（原型当前） | 空心圈 `idle` | `未配置`（neutral） | **一键创建** | 尚未绑定 · 创建后自动成为管理员，可发起隧道与调用 API |
| 已配置 | 绿点 `ok` | 能力标记 `.cap-tag`（**不挂"管理员"徽章**） | 配置 | 已绑定 · 管理全部 N 个项目 |

> 已配置态**刻意没有"管理员"徽章**：身份已由名字里的「管理员」三个字承载，
> 再挂一枚徽章就是同一句话说两遍。徽章留给**能力**（隧道 / API）—— 那是名字里读不出来的东西。
>
> 两种状态是**同一张卡**（`data-state`），不是两张卡 —— 随状态变化的内容各自标 `data-only`，
> 由一条 CSS 规则统一切换。**文案始终留在 HTML 里，JS 只改一个属性。**

判据：

- **未配置时不存在"去配置"这一步。** 还没配置的东西没有可配置的对象 —— 动作必须是**创建**。
  绑定之后动作才切成「配置」。写反了用户会点了没反应。
- **两态的视觉差异说的是"要不要你动手"，不是"好与坏"。**
  虚线框 + 空心点 = 这里还没有实体；实线框 + 绿点 = 已经在了。
  还必须与"**已绑定但离线**"（实线框 + 红/黄点）区分开：前者要你动手，后者不用。
- **未配置态必须写明绑定后的结果**（"创建后自动成为管理员"）。
  否则用户是在**盲点创建** —— 他不知道点下去会得到什么。

**特权的归属：属于账号，不属于机器人**（2026-09-11 定案）

`.cap-tag` 挂在**机器人**名字旁，天然会被读成"**这台机器人**拥有特权"。真实的授权模型是：

| 问题 | 答案 |
|---|---|
| 谁有权发起隧道 / 调用 API？ | **该机器人绑定的飞书账号**（人）。判定是 openid 精确匹配。 |
| 那机器人是什么？ | **承载与转达者** —— 它把特权命令转成动作，本身不"拥有"权限。 |
| 其他机器人收到「隧道」命令？ | 回「⛔ 无权操作：该命令仅管理员机器人受理」。 |

> 所以 `.cap-tag` 的语义是「**承载**管理员能力」，行使者必须点明是绑定的账号
> （原型 tooltip：`承载管理员能力 · 隧道与 API 特权由该机器人绑定的飞书账号行使`）。
> 写成"只有管理员**机器人**可发起"会把特权说成机器人的属性，与实现（权限在**人**）冲突 ——
> 这不是措辞问题：它会让用户对"谁能开隧道"形成错误的默认预期，而那个预期在多机器人下会直接变成误操作。

**创建入口有两个落点，同一个流程：**

| 入口 | 位置 | 用于 |
|---|---|---|
| `一键创建` | 管理员位卡片内 | 创建第一台（自动成为管理员） |
| `＋ 一键创建飞书机器人` | 列表底部 | 继续创建，从第二台起 |

两者**共用现有飞书创建流程**（Device Flow 扫码，见 5.4.2），不新开元器；都**支持预设提示词**。
差别只在"是不是第一台"，不在流程 —— 所以不写两个名字，也不做两个流程。

##### 5.4.2 「一键创建」= 一张二维码，不是一张表单

> **形态不是设计出来的，是流程决定的。** 真实实现是飞书 Device Flow（`internal/larkreg`）：
> `POST /api/larkreg/start` 拿到一个授权链接 → 渲染成二维码 → 用户用飞书扫 →
> `GET /api/larkreg/poll` 轮询到成功、服务端落盘凭据。
> **创建这个动作发生在用户的手机上，桌面上点按钮什么也不会发生** ——
> 所以这个弹层里**没有「创建」提交按钮**。它也是最容易被"顺手加回来"的东西，回归脚本显式守着。

省掉的仍然是**决策**：渠道（飞书，入口名字已写明）、身份（首个绑定即管理员）、
权限（新建默认不含隧道与 API）三项**都已由规则定死**。它们不再占一张三行结论表，
而是压成标题下的**一句话** —— 二维码现在是主角，结论表会把它挤下去。
唯一要用户给的输入还是**预设提示词**，位置在扫码区**之后**：它正好填在等待扫码的空档里，
但不该挡住码。

四个状态（`data-stage` 单属性驱动，不为状态额外维护 class）：

| 状态 | 触发 | 用户看到 | 出路 |
|---|---|---|---|
| `gen` | 打开时 | 遮罩 + 转圈，状态行"正在生成二维码…" | 取消 |
| `scan` | 链接就绪 | 二维码 + 有效期倒计时 + 人的三步 | 扫码 / 取消 |
| `busy` | 手机确认后 | 扫码区换成「✓」遮罩 + 机器侧三步 | 不可关 |
| `dead` | `expire_in` 到点 | 码变淡 + 遮罩，红色状态行 | **重新生成** |

五条判据：

1. **必须有「生成中」。** `start` 接口要等链接出现（内部最多轮 3s），
   直接显示二维码等于假装这件事不花时间。
2. **状态行与指引链分工不重叠。** 状态行说"机器现在在干什么"（等待你扫码确认…），
   指引链说"你该干什么"（打开飞书 App → 扫一扫 → 确认授权）。遮罩**只出图标、不出文字**：
   文字一律归状态行，因为它是四态里都存在的那个元素，用户永远在同一个地方读状态。
   遮罩再写一遍同样的话，就是同一句说两遍（这条实际踩过：失效态里"已失效"曾写了两遍）。
3. **进行态不抽走扫码区。** 整块抽掉会让弹层高度从 ~430px 塌到 ~220px，视觉上猛跳一下；
   换成「✓」遮罩既保住高度，又交代了"人那一步已经过了"。
4. **失效不是"提示一下但仍能用"。** `expire_in` 到点就是真的不能再扫了，所以必须**同时**
   给出重新生成 —— 否则用户卡在一个没有出路的界面上。且它**复用同一个 `generateQr`**，
   不然会长出第二条二维码流程。
5. **二维码不跟随主题。** 扫码器只认深色模块 + 浅色底，深色模式下一反转就扫不出来。
   所以底色与模块色**都写死**，它在两种主题下都是"一张白卡"（生产端返回的 PNG 同理）。
   这是全站唯一一处**故意不跟随主题**的配色，回归脚本用断言钉住 ——
   否则日后"统一深色 token"的改动会顺手把它一起反转掉。

**仍然成立的两条：**

- **两个入口打开同一个弹层、走同一个函数。** 差别只在"是不是第一台"，
  而这一条**由当前状态算出、不由入口决定**（`outcomeHtml`）—— 管理员还没确立时，
  两个入口进来得到的都是第一台。写两套流程，等于在"从哪进来"上凭空长出一套规则。
- **结果落在卡片上，不只落在提示里。** 完成后卡片**就地**从未配置切成已配置，
  填过的提示词写回卡片描述。Toast 会消失，卡片不会 —— **承诺的兑现要留在原地。**

实现要点（原型已固化，回归脚本守着）：

- **弹层的直接父节点必须是 `.viewport`**，且 `.viewport` 要 `position: relative`。
  插错一层，`absolute` 就会相对**初始包含块**（整个浏览器窗口），
  移动端的下沉对齐与宽度撑满会**静默失效** —— 样式不报错，只是不生效。
  这是本次实际踩到的：弹层被插到了 `#viewport` 外面（锚点里的 `</div>` 闭合的其实是 viewport）。
  回归脚本用几何断言守着（贴底 0px / 撑满 398px），比肉眼看截图可靠。
- **不用 `position: fixed`**：`fixed` 会跳出 `.viewport` 的 `overflow:hidden` 跑到浏览器窗口上。
  弹层属于这个 app，必须被裁在设备框里，移动端模拟才成立。
- **`visibility` 的过渡方向必须不同**：展开 `0s`（立刻可聚焦），收起延迟到淡出结束。
  给两者同一个时长，展开的头 180ms 里元素仍不可聚焦 —— `focus()` 会被**静默**吞掉。
- **关遮罩用 `mousedown` 而非 `click`**：在输入框里拖选文本、松手时落在遮罩上，
  `click` 会把它误判成"点了遮罩"而关掉弹层、丢掉已输入的内容。
- **遮罩不加模糊**，用已定义的 `--overlay` token。弹层是个操作面，
  背后那张卡片（管理员位）正是这次操作的落点 —— 糊掉它没有好处，只多一层开销。
- **桌面居中弹层 / 移动端底部 Sheet**，与变更反馈同一套降级规则。
  窄屏还要守一条：二维码**保持正方形且不缩水**（`196×196`）—— 它是这个弹层唯一必须真的能用的东西。
- **焦点三件套**：打开后聚焦**弹层容器**（`tabindex="-1"`）、Esc 关闭、
  关闭后**焦点归还给触发它的那个按钮**。聚焦容器而不是提示词输入框 ——
  主交互在手机上，桌面上第一个可聚焦的控件不该是它；进容器是为了让读屏念出标题。
  代价是焦点陷阱要额外处理"焦点停在容器上"：容器不在可聚焦列表里，
  不显式拦，`Shift+Tab` 会退到遮罩背后去。
- **倒计时的秒数从 `data-qr-ttl` 读**，对应接口的 `expire_in`（SDK 默认 600s）。
  之所以让它可从 DOM 读，是为了让回归脚本把它调小去验失效态，而不必真等十分钟 ——
  走的是同一个定时器、同一套过期处理，只是秒数小。
- **模拟扫码入口是原型专用的。** 真实环境这一步由 `poll` 轮询感知，原型没有服务端，
  所以给一个**明标了「原型演示」**的假入口，否则这条流程在原型里走不下去。
  它用虚线 + 弱色，与真按钮明确区分 —— 它不是设计的一部分，断言守着这个标签。

##### 5.4.3 手动配置：有提交按钮的那一半

弹层由 `data-mode` 分两半：`scan`（默认）与 `manual`。**同一个弹层、同一份「预设提示词」、
同一段落卡逻辑**（`finishRobot`）—— 开第二个弹层就会有两份落卡逻辑，两边迟早不一样。

> **同一个弹层里，提交按钮「有」和「没有」同时成立，判据只有一条：
> 创建这个动作发生在哪一端。**
> 扫码时动作在用户的手机上（`poll` 轮询感知），桌面上点按钮什么也不会发生 —— 所以没有提交按钮；
> 手动时动作就在本页（`POST /api/larkreg/config`）—— 所以**必须**有。

字段（对齐现有 `LarkConfigModal.vue` 的手动页签）：接入方式（`longconn` / `webhook`）、
App ID、App Secret，`webhook` 下追加 Verify Token / Encrypt Key，末尾是共用的预设提示词。

四条判据：

1. **次要入口放在页脚左侧，低强调（无边框、次级文字色）。** 它不是流程的一部分，
   是"这条路走不通时"的旁门，不该跟主路径抢注意力。
   放页脚而不是扫码区里的原因是**四态恒在**：`gen`（码还没生成出来）与 `dead`（码已过期）时
   恰恰最需要它，放进扫码区就会跟着一起藏起来。
2. **描述跟着模式走。** `outcomeHtml(first, manual)` —— 手动模式下不再写"扫码后"。
   那段话是决策依据（"点下去会得到什么"），留一句与实际不符的就是在骗人点头。
3. **`webhook` 的两个字段是条件存在，不是灰着占位。** 长连接模式下它们**根本不存在** ——
   灰着的字段会让人怀疑自己是不是漏填了。
4. **缺字段不静默**：就地报错 + 把焦点送到那个字段。点一下什么都没发生是最差的一种"反馈"。

**它兜的不是"外网"** —— 见 5.4.4：`/api/larkreg` 连 `/config` 一起都是仅内网，
外网下这条路同样是死的。它兜的是"码走不通"：扫不了、组织里已有现成应用、要走 webhook 模式。

##### 5.4.4 仅内网可达的操作：入口就地禁用，不做全局横幅

`/api/larkreg` 的 **start / poll / status / config 五个端点全部**挂在 `BindOpGateMiddleware`
后面，外网一律 403（现有实现直接显示"⚠️ 仅内网可配置渠道"）。

> **把"不行"提前到入口，而不是让人点开才发现。**
> 禁用态必须**自解释**：它连点击都没有，没有 hover、没有 toast 能替它说话 ——
> 唯一能说话的只有**长在它旁边的那行字**。所以原因写在卡片内（`.ag-warn`），
> 不写进 `title`、不写进 toast。

四条判据：

1. **禁用的是"要调这些接口的那几处"，不是一整块。** 标 `data-needs-intranet` 的才受影响；
   工作区、审批、外观都不依赖这些接口，照常可用。**不做全局横幅** ——
   一个横幅会把"只有这一处不行"说成"整个设置页都不行"。
2. **只禁一半 = 留下一个洞。** 管理员卡的创建/配置、列表底部的「＋ 一键创建飞书机器人」，
   以及运行时追加的机器人卡（`appendRobot` 后要重跑 `applyNet()`），**全部**要禁。
   留着任何一个，用户就会去点它，然后发现不行 —— 正是要消灭的体验。
3. **必须真的 `disabled`，不是只做视觉灰化。** 灰化只是"看起来不能点"，
   读屏不会念、回车仍会触发 —— 说的是另一回事（与"状态以 aria 为唯一真相"同一原则）。
4. **原因不能被禁用态的视觉处理一起削弱。** 底部入口的禁用**只压边框与标签，不整块降透明度**：
   整块 0.55 会把橙色原因淡到 2.4:1，等于把唯一要让人看懂的东西写没了。
   同理，窄屏默认隐藏的补充说明在禁用态**必须放出来**（它就是原因本身），
   但**只放"原因"那一行** —— 规则不限定就会把无关文案一起放出来（这条实际踩过）。

**原描述不替换成原因。** 禁用时卡片仍保留"创建后自动成为管理员，可发起隧道与调用 API" ——
**门锁上了，不等于要把这扇门是干什么的藏起来。**

> 副作用：外网下卡片会多出"原因"一行，状态点若不改就会掉到两三行之间、
> 看着像标在了别的东西上。所以卡片里的状态点 `align-self: flex-start`，**跟着名字走**。

**三条边界：**

1. **列表而非开关矩阵。** 现状只有一个管理员位，但列表形态是为多机器人准备的；
   单行形态届时必须重写结构，列表形态只需多一行。**为已知的下一步留结构，不为未知的可能留抽象。**
2. **管理员由「首个绑定」自动确立，不是要用户先决定的事。**
   第一台绑定的机器人自动成为管理员 —— 把"谁是管理员"从一次决策降级成一条规则，
   创建时不必多问一句。它写在组说明里而不是做成设置项，正因为**它没有可选的余地**。
3. **权限默认值写进入口本身。** 创建入口的说明明写 **仅管理员含隧道与 API 权限**。
   默认值放在入口处而不是创建后的配置页 ——
   它是"点不点"的判断依据，不是"建完再调"的参数。

> **能力标记属于「已配置态」，可见时只出现一处。** `.cap-tag` 标在管理员名旁，
> 可见处多于一处就等于这条边界没守住。第一轮创建后它出现在管理员卡上，
> 之后创建的成员都不带 —— **差异靠缺席自解释**。
> 注意"未配置时不显示"和"不存在"是两件事：它在 DOM 里始终只有一份，
> 未配置时由 `data-only` 隐藏 —— 结构要能随状态切换，所以它必须一直在 DOM 里。
>
> **对照组不再需要预先摆好。** 早先为了让能力标记有对照物，在列表里直接写了一台非管理员；
> 现在第二轮创建会自然产生它（`飞书 · 机器人 2`，成员身份，无能力标记）。
> **假数据换成了真交互** —— 同一件事不必说两遍，也不必为了演示而伪造一条记录。

> **渠道是机器人的属性，不是它的上级分类。** 飞书机器人与企业微信机器人是**同一类东西**：
> 各自一次独立绑定、各自一个 IM 身份、各自独立授权 —— 在列表里是**平级的条目**，
> 不是"机器人"下面分出来的两个组。渠道已经写在名字前半截里（`飞书` / `企业微信`），
> 再套一层分组，就是**把刚删掉的"智能体"换个名字加回来**：
> 用户照样会问"这两个组是什么关系"，而答案仍然是"没有区别"。
> 校验脚本对渠道分组头（`.agent-group`）做了拦截 —— 将来接第二个渠道时，
> 正确做法是**往同一个列表里加一行**，不是新开一个分组。
>
> 真正需要区分的是**能力**，而能力由**配置**决定、不由**渠道**决定 ——
> 「能否发起隧道 / 调用 API」看的是这台机器人是不是管理员，
> 与它挂在飞书还是企业微信上无关。把渠道当成能力差异，会在换渠道时凭空多出一套权限规则。

> **不为多机器人预先建模。** 目前只做三件事：列出机器人、标出能力、给出创建入口。
> 「不同机器人配置」的具体字段（各自绑定哪个 IM、各自能碰哪些项目）等真正动工时再定 ——
> 现在画出来的配置页，多半会在需求落地时被推翻。一键创建**复用现有配置**，
> 不引入新的创建流程（原型内触发说明性提示即可）。
> 管理员的**转移与回收**（首台被删除后谁接手）属多机器人协同范围，本次不建模。


**连接状态收敛为 1 处**（本次一并修掉的信息重复）：

连接状态一度同时出现在**侧栏底部**、**仪表盘头部徽章**、**设置入口文案**三处，
其中两处不可点。这违反已为任务列表确立的「一处数据一处渲染」。收敛后：

- 侧栏底部合成**一项**：`设置 ● 连接正常` —— 状态是这一项的**行尾元数据**，
  顺着它点进去就是连接的详情与重连。**一条死信息变成了入口。**
- 仪表盘头部的连接徽章**删除**。
- 连接详情只在设置的「连接与账号」组里有一份完整实现。

### 5.5 主题：偏好与生效值必须分离

主题从二态改为**三态**：`跟随系统 / 浅色 / 深色`，**默认跟随系统**。

- **偏好 ≠ 生效值**：偏好可以是"我没选"，而样式表必须拿到具体的一种。
  所以存两份：`data-theme-pref`（偏好，可为 `system`）与 `data-theme`（解析后的生效值）。
  二态开关无法表达"我没选"，系统主题变化时也无从重算。
- 监听 `prefers-color-scheme` 的 `change`，**仅在偏好为 `system` 时**重算生效值。
- **"浅色优先"不等于"默认浅色"**：前者说的是浅色是独立调校的设计、不是深色的机械反转；
  既然两套已对等，替用户先选一个没有依据。
- 原型工具条上的主题切换与设置页**共用同一份状态**（同一 `setThemePref`、同一 `aria-pressed` 同步）——
  这不是第二份数据，是同一状态的两个视图。工具条只为"不离开当前页也能对照两套主题"而存在。

## 6. 响应式策略

| 断点 | 布局 |
|---|---|
| `< 768px` 移动 | 单列；底部 Tab Bar 仅 3 项（**首页 / 任务 / 设置**，全部为页面切换）；侧边栏隐藏，任务浏览改由底栏「任务」进入整屏任务浏览器页（内容同侧栏树）；待审批组堆叠为单列；决策卡与输入 sticky 吸底；变更反馈改为**整屏**（顶部分段切换），不套用桌面收起态（见 5.2.1）；设置页每行的控件换行到第二行占满整行（窄屏控件不得与标签抢宽度，见 5.4）；任务浏览器页头部动作分行（见 6.1.5） |
| `768–1279px` 平板 | 单列 + 内容区 `max-w-3xl` 居中；Feedback 走 Drawer（420px） |
| `≥ 1280px` 桌面 | 侧边栏 240px（含任务树）+ Timeline `1fr` + Feedback **默认收起 46px**（点击展开 420px）；Settings 单列 `max-w-[760px]` 左对齐 |

- 侧栏在 `< 1024px` 自动收起为图标条（宽 56px），≥ 1440px 可手动折叠。
- **侧栏含任务树，但不含任何"第二份内容区"** —— 树是导航器（点它跳到详情），
  不是渲染详情的地方。判断某结构能否安全隐藏的标准：
  **先把内容移出（让它属于某个目的地），再谈隐藏控件。**
  侧栏隐藏时（移动端），任务浏览这个能力由底栏「任务」页承接，不是丢失。

### 6.1 任务列表 = 侧栏里的导航树（分组，不是页面）

**当前定案**：任务列表在侧边栏里是一个**分组**，默认展开，其下直接列出所有项目；
项目默认收起，点开才列出该项目任务（按最近更新排序）；点任务 → **主区**展示任务详情。

```
侧边栏
  任务列表  12                 ← 分组头，默认展开，可整体折叠
    ▾ oms-service      5       ← 项目行，默认收起（▸）
        ● 修复订单库存扣减不同步   ← 任务行 → 主区详情
        ● 补齐支付回调单元测试
        …
    ▸ pieqi-web        4
    ▸ infra-terraform  3
```

#### 为什么这里必须有树，而本节早期版本否决过它

早期版本明确写过"侧边栏不放项目树"，理由是**重复**：
当时侧栏有项目树、Dashboard 又在"按项目分组"，同一批任务两处出现。
**那个理由成立，但它针对的是重复，不是树本身。** 现在重复的根源已经消除：

| | 当时 | 现在 |
|---|---|---|
| Dashboard 内容 | 待审批 + 需要注意 + 运行中 + 概览 + **按项目分组** | 待审批 + 本周概览（**零任务清单**） |
| 侧栏树是否重复 | 是（与 Dashboard 分组重复） | **否**（唯一一份任务浏览入口） |
| 主区职责 | 行动面 + 档案面 + 详情，三者混住 | Dashboard / 详情，二者互斥 |

结论：**「消除重复」的正确做法是删掉重复的那一份，而不是连树一起删。**
当时删掉的是 Dashboard 里的分组（改成本周概览）；若同时把侧栏树也删了，
就变成"两处都删、任务无处可浏览"，只能被迫造一个 Tasks 页面 —— 绕回主区膨胀。
现在的分工是干净的：

| 层 | 职责 | 承载 |
|---|---|---|
| 侧栏任务树 | **导航 / 定位**（常驻，广度优先） | 项目 → 任务的两级索引 |
| 主区 Dashboard | **行动**（现在要你处理什么） | 待审批 + 本周概览 |
| 主区 Session | **阅读 / 干预**（深度优先） | 单个任务的 Turn 时间线 + 反馈 |

浏览要广度、阅读要深度，两者抢同一块屏幕必然有一方受损 ——
这就是把任务列表做成主区页面时的真实症状（任务一多主区无限拉长）。

**主区不是「任务列表页」。** 任务浏览是**导航行为**，归属侧栏任务树；
主区只在"你选中了某个任务"时才切换到详情。

| 平台 | 任务浏览入口 | 任务详情 |
|---|---|---|
| 桌面 | 侧栏「任务列表」分组 → 项目树（常驻可见） | 主区 Session |
| 移动 | 底栏「任务」→ 任务浏览器页（整屏，同样是项目手风琴） | 主区 Session |

移动端侧栏被隐藏，无处安放常驻树，因此把**同一个组件**换容器渲染成整屏页。
数据源唯一（`PROJECTS`），折叠状态唯一（`openProjects`），两端不维护两份清单。

> **曾被否决的方案**（记录以免重蹈）：
> ① 底栏第 5 项「项目」+ 底部 Sheet 弹层 —— 底栏各按钮视觉相同，4 个切屏、1 个弹层，
> 违反一致性；iOS HIG / Material 明确 Tab Bar 每一项都应是顶层目的地，不应触发 Modal。
> ② Dashboard「按状态 / 按项目」分组切换 —— 解决了底栏一致性，
> 但在桌面端与侧边栏项目树重复出现同一批任务。
> ③ 仅做渐进披露、双栏布局 —— 用布局技巧掩盖职责不清，任务一多仍然失控。
> ④ 「按项目分组的长列表」（组头 + 组内任务全部直接铺开）—— 看似已经分组，
> 但组头并不能折叠，12 个任务仍全量铺在页面上，等于**分组只做了标签、没做收纳**。
> ⑤ 把任务列表做成**主区页面**（Tasks 页）+ 侧栏树同存 —— 两处渲染同一批任务；
> 只留主区页又让"浏览"挤占"阅读"的屏幕。**终态：树在侧栏，主区只给详情。**
> 收敛路径的共同教训：**先问"这块内容该不该在这里"，再问"它该放哪个位置"。**

**实现要点**：
- 项目清单以常量集中定义（`PROJECTS`），是两处渲染的**唯一数据源**。
- 任务树的选中态是 `.sb-task.is-active`，**只在会话页生效** —— 树表达"我在哪"，不是"我看过什么"。
- 分组头（「任务列表」）**不带 `data-nav`**：它是分组，不是目的地，不参与导航高亮。
- 排序方式只有一种（最近更新）时**删除排序下拉**，把口径写进 `title` 与文档即可。
- 「按空间筛选」下拉**不做**：列表主体已是全部项目，再筛同一维度就是第二次收窄，
  与树本身互相打架（筛完只剩一个项目 = 用下拉替代一次点击）。

#### 6.1.1 侧栏任务树规格

| 状态 | 表现 |
|---|---|
| 分组头 | 「任务列表」+ 任务总数徽章；点它整体折叠/展开；**初始展开**（用户要"下面直接看到项目"） |
| 项目行 | chevron + 项目名 + 任务数徽章；**默认收起**，各自独立折叠 |
| 展开态 | chevron `›` 旋转 90° 变 `⌄`，`aria-expanded` 同步 |
| 任务行 | 状态点 + 任务名；点击 → 主区 Session，该行高亮 |
| 排序 | 项目内任务按**最近更新升序**（最新在最上） |

**默认收起的收益**：收起态树高恒为「项目数」条，不随任务数膨胀。
侧栏是常驻的，高度预算固定，树的复杂度必须是 O(项目数) 而非 O(任务数)。

> 折叠态存在 `openProjects`（项目名 → 是否展开）中，**跨容器与跨视口共享**：
> 侧栏展开的项目，切到移动端任务浏览器页仍是展开的，反之亦然。

#### 6.1.2 侧栏任务行只放名称（实测取舍）

侧栏 240px，减去 `sb-head` 左右各 12px、任务行缩进 26px、状态点 6px 与间距，
**只剩约 168px 给任务名**。是否再塞一个相对时间列，实测（`_measure.mjs`）：

| 方案 | 名称可用宽度 | 任务名被截断 |
|---|---|---|
| 名称 + 相对时间 | 121px | **4 / 5（80%）** |
| 仅名称 | 167px | **0 / 5（0%）** |

**结论：不放时间。** 侧栏是导航器，名称是扫描目标；截断 80% 的名称会让
"找任务"这件事本身失效，而时间是**校验**信息，不是**定位**信息。
时间与改动量属于主区详情（`更新于 2 分钟前`）与移动端任务浏览器页，不属于导航。

> 一般化规则：**容器宽度不足时，先砍元数据，别砍主标签。**
> 判断标准是"这一列是用户用来找东西的，还是用来确认东西的" —— 前者不能截断。
> 这条规则需要一个**可执行的回归断言**（`_verify.mjs` 里测 `scrollWidth > clientWidth`），
> 否则后续加列时会无声地退化。

#### 6.1.3 折叠动画：不测量高度

用 `grid-template-rows: 0fr → 1fr` 配 `overflow: hidden` 做展开动画，
**不读 `scrollHeight`、不写内联 `max-height`**。任务列表内容是动态渲染的，
按像素测量会在筛选/搜索后失准；而 `0fr → 1fr` 交给浏览器排版计算，天然自适应。

收起态同时设 `visibility: hidden`（延迟到动画结束），
否则被裁剪的任务行仍在可聚焦序列里，键盘 `Tab` 会跳进看不见的元素。

点展开/收起时**只切 class，不重绘整棵树**，保证动画不被打断。
（侧栏树走整树重绘 —— 行数少且无动画，简单优先；移动端手风琴有动画，故必须切 class。）

#### 6.1.4 移动端任务浏览器页（渐进披露）

移动端这一页保留搜索与状态筛选，因为它是整屏、空间充足。三条行为边界：

- **搜索时自动展开命中的项目**，否则用户还要"先搜、再逐个点开找在哪"，
  披露反而变成障碍。搜索词命中**项目名**时展示该项目全部任务（而不是空列表）。
- **筛选后无匹配任务的项目置灰且不可展开**（`opacity .52` + `disabled`），
  而不是从列表里消失 —— 保持"列表永远展示所有项目"的稳定性，同时如实告知无匹配。
- 筛选态下**隐藏「展开全部」**（已自动展开，手动开关会与自动行为语义打架）。

#### 6.1.5 移动端头部：行动作分行

任务浏览器页只有移动端可达（桌面由侧栏树承接），布局直接按窄屏写：

- 标题 + 副文案占第一行，操作按钮占第二行（`flex-wrap: wrap`）。
- **「新建任务」占满整行**，补上底栏没有的新建入口，也满足拇指点击区要求。
- 项目行右侧的状态聚合在移动端隐藏，避免与项目名抢宽度。

### 6.2 Dashboard 只放「待审批 + 本周概览」

**当前定案**：仪表盘只有两个区块，一个都不多。

| 区块 | 回答的问题 | 数据 |
|---|---|---|
| 待审批（`#approvalZone`） | "**现在**什么卡在我这里？" | 审批卡，按风险降序 · 同风险按时间升序；L3 必须内联二次确认 |
| 本周概览（`.insight`） | "这周整体干得怎么样？" | 回顾性指标，见下表 |

**已从仪表盘移除**（三块，各有明确去处）：

| 移除的区块 | 移除原因 | 去处 |
|---|---|---|
| 状态统计 chip 行（全部/运行中/待决策/已完成/失败） | 它是"状态分布概览"却长成了导航，用户点击后要跳去别的页看结果 —— 一个控件同时承担两种职责 | **删除**。任务浏览归侧栏任务树，状态用任务行的状态点表达 |
| 「需要注意」（失败任务） | 与「待审批」同属行动面但不是"等你决策"，而是"出错了"；混在一起会让焦点区的语义从"要你点按钮"变成"要你看一眼" | 归入任务树 —— 失败任务在项目里带红色状态点，展开即见 |
| 「运行中」（实时活动） | 纯展示型：用户不在这里做任何操作，却占据了行动面的整块屏幕 | **删除**。运行状态由任务树的状态点承载 |

**判据**：行动面只保留「**需要你做决定**」的内容。
待审批天然满足（有按钮要点）；本周概览是回顾性补充，不随历史无限增长。
"运行中"和"失败任务"都不需要你在此刻做决定 —— 它们是**状态**，不是**待办**。

> 这一条要与 §6.1 的侧栏树一起看：Dashboard 腾出的信息并没有丢，
> 而是搬到了侧栏任务树（状态点）与本周概览（趋势）。**"搬走了"不等于"删掉了"。**

**本周概览**（`.insight`）—— 一组**回顾性**指标，与待审批的"现在要做什么"互补：

| 指标 | 值 | 为什么有意思 |
|---|---|---|
| 完成任务 | 12 `+3 较上周` | 配 7 天迷你柱状图，一眼看出趋势，今天那根用 accent 实色 |
| 平均耗时 | 18 分钟 | 衡量 agent 自主完成效率 |
| 代码改动 | `+842 −317` · 27 个文件 | 产出规模，比"完成数"更真实 |
| 一次通过率 | 75% · 9/12 | 衡量 agent 质量：多少任务无需人工返工 |

**边界**：这些是趋势与质量指标，**不是状态统计** —— 概览回答"这周干得怎么样"，
不回答"现在各状态有几个"（后者已由任务树的项目计数与状态点回答）。

### 6.3 Dashboard 为什么曾经失控（保留复盘）

Dashboard 曾同时是**行动面**和**历史档案**：焦点区（待决策/失败）+ 运行中 + 最近完成
+ 按项目分组 + 概览，全部单列堆叠。7 个任务时刚好一屏；按 20 个任务估算总高约 2500px，
需滚三屏，而"需要你处理"滚出视口后 Dashboard 就失去了存在意义。

> **不要靠断点切换布局来救长度。** 曾考虑「桌面双栏、移动单列」：≥1280px 拆主列/侧列。
> 它确实能减半长度，但引入了一个更贵的东西 —— **同一产品在不同宽度下是两种结构**，
> 用户的心智模型、文档、回归测试都要维护两套。先问"这块内容该不该在这里"，
> 再问"它该放在哪个位置"。

**演进路径**（记录以免循环）：

| 版本 | 做法 | 问题 |
|---|---|---|
| ① | Dashboard 全量展示（状态 + 项目 + 最近完成） | 无限拉长，~2500px |
| ② | 拆出 Tasks 页承载全部任务 | Tasks 页与侧栏树重复；主区被浏览挤占 |
| ③ | 去侧栏树，Dashboard 加「本周概览」 | 重复解决了，但浏览无处安放，Tasks 页仍是主区 |
| ④ | **终态**：任务列表降级为侧栏分组（树），Dashboard 只留待审批 + 本周概览 | — |

**收敛路径的共同教训**：**先问"这块内容该不该在这里"，再问"它该放在哪个位置"。**

## 7. 无障碍（WCAG 2.1 AA）

- **对比度**：正文 ≥ 4.5:1（`--text-tertiary` 为最低档，已实测 4.8:1）；非文本 UI（边框、状态点、图标）≥ 3:1。
- **不靠颜色单独表意**：每个状态色必须配图标或文案（✓ / ⚠ / ✕）。Diff 的增删行除颜色外，`+` `-` 前缀必保留。
- **键盘**：全功能可达；Tab 顺序符合视觉流；Timeline 支持 `j/k` 事件跳转、`/` 聚焦输入框；Modal/Drawer 焦点陷阱 + Esc 关闭 + 关闭后焦点归还触发元素。
- **焦点可见**：统一 `:focus-visible` 3px `--accent-ring`，禁止 `outline: none` 裸删。
- **语义**：`<header> <nav> <main> <aside>` 地标齐全；列表用 `<ul>/<li>`；图标按钮必带 `aria-label`；Toast 区 `aria-live="polite"`，错误 `role="alert"`。
- **动效**：遵循 `prefers-reduced-motion`；呼吸点仅 2s 低频，不闪烁（频率 < 3Hz，避免光敏风险）。
- **触控**：最小 44×44px，相邻可点元素间距 ≥ 8px。
