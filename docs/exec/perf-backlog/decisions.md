## D-001 · 用执行文档而非对话做交接（2026-10-22）

**决策**：本次任务的所有状态落在 `docs/exec/perf-backlog/`，会话只做决策与验收。

**理由（第一性）**：长任务里只有「判断」不可重建；实施与验证都能由代码+证据重推。
所以状态必须外置到不占上下文、且压缩不可摧毁的载体。

**否掉的**：
- 在同一个会话里顺序做完 7 条 —— P1/P2 之间必然压缩，最先丢的是 P0 的**新实测数字**。
- 用 `subagent_fork` 承接下一段 —— 它继承全部历史，总 token 不降，省不了上下文。

## D-002 · 复用已存在的 `pieqi-perf-a` / `pieqi-perf-b`（2026-10-22）

**决策**：不新建 worktree，直接用现存两个（分支名 `perf/p0-update-merge`、`perf/p0-payload`
已经和 P0-1/P0-2 对应上）。

**判据**：二者均 0 commits ahead、无本地改动 → 复用零成本。
**替代方案被否**：新建 `pieqi-perf-c` 等。理由是分支语义已正确，再加只会让
`git worktree list` 变长、增加清理负担（`AGENTS.md` 明确要求临时探针不留在列表里）。

## D-003 · 段顺序 A → B，而不是 B → A（2026-10-22）

**决策**：必须先修写锁再量 payload。

**判据**：payload 体积的收益表现为「首屏快」，而首页慢里混着「被 20.6ms 写锁串行化」的
排队时间。先修锁，才能把首屏收益**归因清楚**；反过来做，量到的改善无法区分来自谁。
这条也是 backlog 自己的顺序（P0-1 在 P0-2 前），此处只是把**理由**固化下来。

## D-004 · P0-2 在 API 层窄化，而非改 `TaskSummary` 类型（2026-10-22）

**决策**：在 `listTasks` 里就地遮蔽 `Baseline`。

**判据**（实测）：`internal/api/tasks.go:163-188` 的 handler 自己持有 `*model.Task`。

**额外好处**：`TaskSummary` 同时被 WS 快照（`api/ws.go:121`）使用，改类型会**连带影响快照**，
而快照体积本就不是本次要修的目标；在 handler 内窄化天然只影响列表接口。

⚠️ 这是**段 B 的预判，未实施**。若实施时发现 API 层无法产出窄化后的 JSON（例如 `Task` 的
`Baseline` 字段无法按调用点区分），退回改 `TaskSummary`，并在本文件补记原因。
