# 线上复量：设计方案（2026-10-18）

> AGENTS.md 的验收纪律第 2 条是「**部署前**拿待部署的那一份再验一次，**部署后**线上复量」。
> 前一半已经由 `e2e/layout` + `visual` + `interaction` 三层落地；**后一半一直是空话**。
> 本文把它变成可执行的规格。
>
> 本文只定**方案**，不含实现。实现前请先过 §6 的三条待定项。

---

## 1. 为什么不能直接拿现有用例指线上

现有 58 例全部依赖 `/__e2e/detail` 这个**夹具页**。它只在 `vite --mode e2e` 的入口里
存在（`e2e/boot-fixture.ts`），生产二进制里**根本没有这条路由**（`registerStatic`
的 SPA fallback 会把它渲染成 index.html → 首页空壳）。

所以线上复量必须是**另一组用例**，只能打真实页面：

| 现有夹具用例 | 线上只读用例 |
|---|---|
| 打 `/__e2e/detail?mode=xxx`（自造数据） | 打 `/dashboard`、`/sessions/<真实id>`（真实数据） |
| 数据可控 ⇒ 可以逐像素比基线 | 数据每天变 ⇒ **只能比结构/几何/可达性**，不能比像素 |
| 有 mock 后端兜底 | 打真实服务 |

**关键判断：线上复量的价值不在"像素没变"，而在"这屏还能用"。**
拿线上数据和 dev 基线比像素必然全红（真任务标题、真 diff 数字都不同），
那种红没有任何信息量。

## 2. 前提（已核实）

| 前提 | 结论 | 依据 |
|---|---|---|
| 内网访问是否需要 token | **不需要**（internal IP → 全放行） | `internal/auth/auth.go:11` |
| SPA 路由如何兜底 | 未命中的非 API 路径一律返回 `index.html` | `cmd/pieqi/web.go:41` |
| API 路径兜底行为 | `/api/*` 未命中返回 **404 JSON**，不回退 SPA | `cmd/pieqi/web.go:27` |
| 写操作的鉴权 | 与读同一套（内网放行）；**这正是最危险的地方** | 同 auth.go |

> ⚠️ 第 4 条是本方案的核心风险：**从内网访问线上实例时，读和写的鉴权强度相同**。
> 一次误点「允许一次」就是一次真实的工具放行。所以本层的第一条纪律是
> **物理上不能写**（见 §3.1），而不是"小心别点"。

## 3. 三条设计约束

### 3.1 只读：靠机制保证，不靠自觉

**判据：线上用例的浏览器上下文必须让任何非 GET 请求发不出去。**

```ts
// 每个线上用例的第一行
await page.route('**/api/**', (route) => {
  const m = route.request().method()
  if (m === 'GET' || m === 'HEAD') return route.continue()
  // 非 GET 一律就地失败 —— 不是 fulfill 一个假 200，而是让它**响亮地失败**：
  // 静默假装成功会让"点了没反应"变成"看起来正常"，掩盖真实的误触。
  return route.abort('blockedbyclient')
})
```

配套断言：用例结束时 `writes.length === 0`（用 `page.on('request')` 自己记账）。

> 为什么不只靠"不点敏感按钮"：按钮文案会改、`aria-label` 会改、
> 未来某页可能有一个默认聚焦的提交按钮。**白名单式的"记得别点"必然会失效。**

### 3.2 不碰真实数据：浏览即可，不进入任何"有副作用"的路径

- 允许：打开页面、滚动、展开只读折叠区（如「更早的 N 轮」——纯前端挂载，不发请求）
- 禁止：任何 `intervene` / `cancel` / `rewind` / `preview/start` / `restart` 路径
- **不确定是否只读的交互，一律不做**（与 `toolkind_map.go` 同一条保守原则：
  证明不了安全就当它不安全）

### 3.3 判据只用"与数据量无关"的指标

线上数据每天变，所以**不能**比 DOM 节点数、不能比像素、不能比 LCP 绝对值。
可以比的：

| 指标 | 为什么与数据无关 | 判据 |
|---|---|---|
| 整页横向溢出 | 只看 `scrollWidth vs clientWidth` | `=== 0` |
| 关键元素被遮挡 | 与内容多少无关 | 无 |
| 主行动按钮在视口内 | 与内容多少无关 | 是 |
| 控制台错误 | 与数据无关 | 无（除 WS 噪声） |
| 首屏可见区块齐全 | 结构问题，不是内容问题 | 全部存在 |

**这些恰好就是"这屏还能不能用"的定义**，也正是 AGENTS.md 第 2 条真正要保的东西。

## 4. 用例规格（4 条）

每条都必须是"线上恒真"的 —— 不依赖任何具体任务、具体标题、具体数字。

### R1 · Dashboard 可进入且主行动可见

```
goto /dashboard
等 [data-testid="..."] 就绪（无则等 nav 出现即可）
断言：
  · 无整页横向溢出
  · 控制台无 error（忽略 WS 重连噪声）
  · 页面标题/主标题存在（路由没被踢回登录/空壳）
  · 若存在待审批卡，则其「允许一次」完整在视口内
```

> 为什么允许"若存在"：线上可能没有待审批项。**有则必须可见，无则跳过** ——
> 这是线上用例与夹具用例最大的不同：**不能假定数据形状**。

### R2 · 会话详情页可进入（取一个真实任务）

```
从 GET /api/tasks 取第一个任务 id（只读请求）
goto /sessions/<id>
断言：
  · 时间线容器可见
  · 输入框（composer-bar）存在且发送按钮在视口内
  · 无横向溢出、无控制台错误
  · **不做任何点击**（输入框只 verify 可见，不 fill）
```

### R3 · 设置页可进入且开关可交互

```
goto /settings
断言：
  · 四组标题齐全
  · 至少 L0/L1 两个开关 enabled（= settings 加载成功）
  · 无横向溢出
```

### R4 · 静态资源与 SPA 兜底健康

```
断言：
  · GET / 返回 200 且包含 <div id="app">
  · GET /assets/ 下的某个 js 返回 200（从 index.html 里解析出一个 src）
  · GET /api/tasks 返回 200（鉴权通路正常）
  · GET /api/nonexistent 返回 404 JSON（不是 HTML —— 区分"路由坏了"与"接口没了"）
```

> R4 是唯一不依赖浏览器的（纯 HTTP），但它能在**部署刚完成、CDN 还没热**时
> 立刻抓到"二进制换新了但前端资源 404"这类问题。

## 5. 怎么跑（配置形态）

```bash
# 线上复量：独立 project，独立 baseURL，默认不参与 npm run test:e2e
ONLINE_BASE_URL=http://127.0.0.1:3000 npx playwright test --project=online
```

`playwright.config.ts` 里加：

```ts
{
  name: 'online',
  testDir: './e2e/online',
  fullyParallel: false,
  workers: 1,          // 只读但顺序跑：避免对线上造成突发压力
  use: { baseURL: process.env.ONLINE_BASE_URL || 'http://127.0.0.1:3000' },
}
```

三条纪律：
1. **不在默认 `npm run test:e2e` 里** —— 线上复量是**发版动作**，不是每次改代码都跑。
2. **必须显式给 `ONLINE_BASE_URL`**，且**默认值指向 127.0.0.1**（自己这台机器的线上实例），
   不是公网地址 —— 防止误跑。
3. 与夹具三层共用 `e2e/lib/measure.ts` 的采集代码（溢出/遮挡判据同源），
   但**不共用基线**（`e2e/baseline/` 只服务夹具层）。

## 6. 实现前需要拍板的三件事

1. **跑在哪？**
   - (a) 本机 `127.0.0.1:3000`（部署后立刻自查，鉴权走内网放行）
   - (b) 公网域名（需要 token / Cloudflare Access 凭据，且要确认 Access 不会挡 `/assets`）

   我建议先做 (a)：(b) 的凭据管理是另一个问题，且 Access 按 hostname 生效，
   会连带挡住 preview 之类路径（见技能 `cloudflared-quick-tunnel` 的记录）。

2. **"线上"是指哪个实例？**
   如果是本机 3000 跑的就是生产（当前正是这样），那 (a) 就够了；
   如果有独立服务器，需要确认**内网地址**而不是公网域名。

3. **失败怎么通知？**
   线上复量失败应当在发版流程里**挡住上线**，还是只告警？建议先只告警
   （它依赖真实数据形状，偶发红不该阻断发版），跑稳 2~3 次后再考虑阻断。

---

## 7. 与既有纪律的关系

- **不替代前一层**：夹具三层验证"改了没坏"，线上层验证"部署后还能用"。两者判据不同。
- **不引入 Web IDE / 录屏**（ADR-0007 非目标清单不受影响）。
- **不复活视觉反馈**（ADR-0013）：本层不做截图采集服务，只做实时断言。
- **隔离原则**：线上层是唯一**故意**指向真实服务的层，所以它的"只读"必须是机制
  （§3.1），不能是约定。

---

## 8. 落地顺序（建议）

```
① 先写 R4（纯 HTTP，最简单，立刻能抓"资源 404"）
② 再写 R1（Dashboard）—— 最常访问、结构最稳定
③ R3（设置页）—— 结构固定，不依赖任务数据
④ R2（会话详情）—— 依赖取一个真实任务 id，最后做
```

每完成一条就跑一次真实实例确认；**四条都稳定跑 3 次以上**再考虑接进发版流程。
