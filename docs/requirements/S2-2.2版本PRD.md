## 1. 版本目标与成功度量

### 1.1 版本目标

把已在 2.1 完成（身份 / 权限 / 回执路由）的多机器人能力**接入任务执行链路**，并收口三处已定案未落地的欠账（Timeline 分组、SW 缓存版本、输入控件组件化）。

### 1.2 北极星指标

**IM 原生建任务成功率** —— 定义：`从 IM 成功创建的任务数 ÷ IM 建任务请求数`。

选它的理由：2.2 的主题是"把 IM 这条主链路接通"，而这条链路此前是**死的**（`OriginChannel` 零写入点）。成功率直接度量"接通了没有"，且失败可归因到具体环节（权限 / 路径 / 系统）。

### 1.3 驱动指标

| 指标 | 口径 | 基线 | 目标 | 归属批次 |
|---|---|---|---|---|
| IM 建任务成功率 | 见 §4.2 | 无（0 —— 能力不存在） | **≥ 95%** | 2.2.1 |
| 回推到达率 | 见 §4.2 | 无（0 —— 能力不存在） | **≥ 99%** | 2.2.1 |
| Turn 分组覆盖率 | 见 §4.3 | 无（能力不存在） | **100%**（有 TurnInfo 的任务） | 2.2.0 |
| 输入控件统一率 | 使用 `components/ui/` 组件的输入控件数 ÷ 全站输入控件数 | **0 / 21**（实测） | **21 / 21** | 2.2.0 |
| 一次通过率 | 见 §4.4 | 无（数据未落盘） | 上线首周建立基线（**不预设目标值**） | 2.2.0 |

### 1.4 健康指标（防"指标好看但体验变差"）

| 指标 | 口径 | 目标 |
|---|---|---|
| IM 建任务端到端回复延迟 | 收到消息 → 回复任务卡，P95 | **≤ 2s** |
| 误建任务率 | IM 创建后被用户立即取消（≤60s）的任务 ÷ IM 任务数 | **≤ 5%** |
| 回推 P95 延迟 | 任务进入 waiting_input / 终态 → 用户收到，P95 | **≤ 5s** |
| 前端回归 | `_validate.mjs` 错误数 / `_verify.mjs` 通过项 | **0 错误 / 200 项全通过** |

## 3. 功能需求规格（EARS + AC）

### 3.1 R1 —— IM 原生建任务 + Origin 链路接通（2.2.1，P0）

**上游依据**：缺口 E1（IM 不建任务）+ B1（`OriginChannel` 零写入点）；决策 D1=c、D2=a（仅绑定管理员）、D3=b（`/项目 xxx`）。

#### 3.1.1 IM 侧交互设计（原型）

**命令集**（与既有隧道命令并列，不冲突 —— 隧道命令已占用「隧道 / 续期 / 关隧道」等词，均不在下列前缀内）：

| 用户输入 | 系统行为 |
|---|---|
| `/项目 <路径>` | 校验路径 → 记为该**会话**的当前项目 → 回复确认（项目名 + 绝对路径） |
| `/项目`（无参） | 回复当前会话已选定的项目；未选定时回复引导 |
| `/任务 <描述>` | 用当前项目**显式**建任务 |
| 裸文本（非以上命令、非隧道命令） | 用当前项目**隐式**建任务 |
| `/帮助` | 列出可用命令（含 `/项目`、`/任务`、隧道命令） |

**会话态**：新增"每个 IM 会话（channel + chatID + botID）的当前项目"这一状态。⚠️ **该状态是 R1 的最小必要新增** —— 没有它，"发一句话就建任务"无处安放（`createTaskReq` 强制要求 `project_path`）。

**D10 ✅ 已定（2026-09-12，用户授权按建议执行）：裸文本直接建任务**，不强制 `/任务` 前缀。
理由：`README.md:3` 的 headline 是「在飞书发消息即可创建任务」，若必须打前缀，承诺即打折。防误触不靠前缀，靠两道闸门：① **必须先选定项目**（选项目是有意识动作，未选定一律不建）；② 建任务后**即时回执**（含任务短 id，可后续纠正）。
> ⚠️ **S3 据此固化一条实现约束**：命令优先级必须是「**隧道命令 → Pieqi 命令 → 裸文本**」。隧道命令不带 `/` 前缀（「隧道」「续期 1h」），若先判裸文本，「隧道」两字会被当成 prompt 建任务 —— 直接破坏 `AC-R1-05`。

#### 3.1.2 EARS

| ID | 类型 | 句式 |
|---|---|---|
| R1-U1 | Ubiquitous | The system shall 对每条进入 Pieqi 模式的 IM 消息**先按命令集解析**；解析为命令者执行命令，**不创建任务**。 |
| R1-S1 | State-driven | While 该会话**尚未选定项目**，the system shall **不创建任务**，并回复引导语（含 `/项目` 用法示例）。 |
| R1-E1 | Event-driven | When 绑定管理员发送 `/项目 <路径>`，the system shall 校验该路径，**校验通过**则记为该会话的当前项目并回复确认（项目名 + 绝对路径）。 |
| R1-E2 | Event-driven | When 绑定管理员在**已选定项目**的会话中发送 `/任务 <描述>` 或非命令文本，the system shall 以该文本为 prompt、以当前项目为 `project_path` 创建任务，并**同时**写入 `Source=im`、`OriginChannel`、`OriginChatID`、`OriginIdentity`、`OriginBotID` 五项。 |
| R1-E3 | Event-driven | When 任务创建成功，the system shall 立即回复**任务短 id + 项目名 + 首行摘要**，并说明进展会推送到本会话。 |
| R1-E4 | Event-driven | When 任务进入 `waiting_input`，the system shall 通过 `OriginChannel` + `OriginBotID` 向原会话推送审批内容（**含风险分级**）。 |
| R1-E5 | Event-driven | When 任务进入终态（`completed` / `failed` / `cancelled`），the system shall 向原会话推送终态摘要；`completed` 时含改动统计。 |
| R1-U2 | Unwanted | If 发送者**不是该机器人的绑定管理员**，then the system shall 拒绝并回复无权限，**且不发起任何模型调用**。 |
| R1-U3 | Unwanted | If 路径校验失败（不在允许集合 / 非 Git 仓库 / 越界），then the system shall 拒绝并回复**具体原因**，且**不改变**当前已选定的项目。 |

#### 3.1.3 AC

| ID | 验收标准（可判定） |
|---|---|
| AC-R1-01 | 绑定管理员在已选项目会话中发一句话 → 任务被创建，且 `source == "im"`、`origin_channel`/`origin_chat_id`/`origin_identity`/`origin_bot_id` **四项均非空**（可查 API 断言）。 |
| AC-R1-02 | 同一句文本从**非管理员**账号发出 → 无任务创建，回复无权限；**该次请求的模型调用数 = 0**（可归因）。 |
| AC-R1-03 | 未选定项目时会话发文本 → 无任务创建，回复含 `/项目` 引导。 |
| AC-R1-04 | `/项目 <非法路径>` → 拒绝且回复具体原因；随后 `/项目` 查询仍显示**转移前**的项目（证明未污染状态）。 |
| AC-R1-05 | 隧道命令（「隧道」「续期 1h」「关隧道」）**仍按原语义执行**，不被解析为建任务（回归）。 |
| AC-R1-06 | 任务进入 `waiting_input` → 原 IM 会话收到推送，且**消息含风险分级**（L0–L3 之一或"未知"）。 |
| AC-R1-07 | 任务进入 `completed` → 原会话收到终态摘要，含改动统计（文件数 / 增删行）。 |
| AC-R1-08 | IM 建任务成功率 ≥ 95%、回推到达率 ≥ 99%（口径见 §4.2；以 2.2.1 上线后首周为观察窗）。 |
| AC-R1-09 | IM 建任务端到端回复延迟 **P95 ≤ 2s**。 |

**R1 明确不做**：不做多轮对话式追问补全（缺项目就引导，不猜）；不做 IM 侧任务列表 / 翻页（仍回 PWA）；不做非飞书渠道的建任务（`OriginIdentity` 依赖 open_id 语义）。

### 3.2 R2 —— 机器人预设提示词生效（2.2.1，P0）

**上游依据**：缺口 A1（消费方为 0）+ C4（明文随列表下发）；决策 D9=a（追加语义）、D9(2)=a+c（不进 API 响应 + 长度上限）。

#### 3.2.1 EARS

| ID | 类型 | 句式 |
|---|---|---|
| R2-U1 | Ubiquitous | The system shall 在组装任务 system prompt 时，把机器人预设提示词**追加**在 `config.yaml` 全局默认 system prompt **之后**（`D9=a`：机器人角色叠加在全局约束**之下**，全局安全约束始终保留）。 |
| R2-E1 | Event-driven | When 任务由 IM 创建（`OriginBotID` 非空），the system shall 使用**该机器人**的预设提示词；`OriginBotID` 为空时（PWA 建的任务）使用全局默认。 |
| R2-U2 | Ubiquitous | The system shall 在**外网可达**的响应（`GET /api/bots`）中**不下发** `sys_prompt` 明文，只下发 `has_sys_prompt: bool`（`D9(2)=a`）。 |
| R2-U3 | Ubiquitous | The system shall 对预设提示词施加**长度上限**（单位 **rune** 而非 byte；具体数值待 S3 定，建议 ≤ 1000），并在**三条写入路径**（`POST /api/bots`、`PATCH /api/bots/:id`、`/api/larkreg` 设备流）**一致**校验。 |
| R2-U2b | Unwanted | If 提交的提示词**超过长度上限**，then the system shall 拒绝并返回**当前长度与上限**。 |
| R2-U3b | Unwanted | If 提示词为**空串**，then the system shall 视为"未设置"（`has_sys_prompt == false`），不注入空段落。 |
| R2-U4 | Ubiquitous | The system shall 保证预设提示词**可持久化**：保存后重启服务仍存在。 |

#### 3.2.2 AC

| ID | 验收标准（可判定） |
|---|---|
| AC-R2-01 | 机器人 A / B 各设不同预设提示词，分别从各自 IM 会话建任务 → 两个任务的 system prompt **分别含 A / B 的预设文本**。 |
| AC-R2-02 | **追加语义可判定**：上述任务的 system prompt **同时包含** `config.yaml` 全局默认内容（证明是追加而非覆盖）。 |
| AC-R2-03 | PWA（无 `OriginBotID`）建任务 → 注入内容 = 全局默认，**不含任何机器人预设文本**。 |
| AC-R2-04 | `GET /api/bots` 响应体**不含**预设提示词明文（对响应体做子串断言）；响应含 `has_sys_prompt` 且取值与实际一致。 |
| AC-R2-05 | **三条写入路径**分别提交超限提示词 → **均被拒绝**（逐条测，防"只校一处可绕过"）。 |
| AC-R2-06 | ⚠️ **回归守门**：保存提示词 → 重启服务 → 提示词**仍在**。（这条专门守 `C4` 的陷阱 —— 修 `C4` 时若误用 `json:"-"`，会让已存提示词静默消失。） |
| AC-R2-07 | UI 上"已设 / 未设"的显示与 `has_sys_prompt` 一致；**不再承诺任何未生效的能力**（回归 A1 的"比不显示更糟"）。 |

**R2 明确不做**：不做敏感信息检测 / 脱敏（`D9(2)` 已否 b —— 需误报治理，2.2 不划算）；不做多机器人提示词模板库 / 版本管理。

### 3.3 R3 —— Timeline 按 Turn 分组（2.2.0，P0 收尾）

**上游依据**：缺口 C1；SPEC §5.2 前半节。
**关键前提（已核实）**：`core.TurnInfo`（`internal/core/feedback.go:59`）**已存在**且已在 feedback bundle 中产出（含 `Turn` / `StartEventSeq` / `UserPrompt` / `Summary` / `Changes`）→ **后端不用新造数据**，R3 的主体是**前端按既有分组渲染 + 联动**。风险因此显著低于原估。

#### 3.3.1 EARS

| ID | 类型 | 句式 |
|---|---|---|
| R3-U1 | Ubiquitous | The system shall 在任务详情时间线中**按 Turn 分组**渲染事件，分组边界取自 `core.TurnInfo.StartEventSeq`。 |
| R3-U2 | Ubiquitous | The system shall 保证分组内展示的文件数与点开后的 diff **同源**（复用**同一份** feedback bundle，不各自再算一遍）。 |
| R3-E1 | Event-driven | When 某 Turn 归属于一次用户输入之后，the system shall 在该分组头部显示该 `UserPrompt` 与其变更摘要（文件数 / 增删行）。 |
| R3-E2 | Event-driven | When 用户在某 Turn 分组点击「查看本轮变更」，the system shall 打开反馈面板并切换到**该 Turn** 的 diff。 |
| R3-S1 | State-driven | While 时间线仍在流式追加（任务运行中），the system shall 保持分组随新事件**增量**更新，不整块重排。 |
| R3-U3 | Unwanted | If `TurnInfo` 缺失（旧任务 / 计算失败），then the system shall 回退为**单组平铺**，**不报错、不白屏**。 |

#### 3.3.2 AC

| ID | 验收标准（可判定） |
|---|---|
| AC-R3-01 | 含 N 次用户输入的任务 → 时间线呈现 **N 个 Turn 分组**，分组边界与 `StartEventSeq` 一致。 |
| AC-R3-02 | 分组头部的文件数 == 点击"查看本轮变更"后 diff 的文件数（**数字同源断言**）。 |
| AC-R3-03 | **Turn 分组覆盖率 = 100%**（口径见 §4.3）。 |
| AC-R3-04 | 旧任务（无 `TurnInfo`）打开详情 → 事件平铺展示，**无报错、无空白**。 |
| AC-R3-05 | 运行中任务新增一轮 → 分组增量出现，已有分组的展开/收起状态**不被打断**。 |
| AC-R3-06 | 与反馈面板联动后，右侧面板 Turn 与 Timeline 选中 Turn **一致**。 |

**R3 明确不做**：不做 Turn 级折叠态的持久化（会话内保持即可）；不做 Turn 间 diff 对比视图。

### 3.5 R5 —— 机器人管理员转移 / 回收（2.2.1，P0 且**先于 R1**）

**上游依据**：缺口 D1；决策 D2=a（仅绑定管理员）+ D7=a（R5 并入 2.2.1 排在 R1 前）。
**为什么是 R1 的前置**：管理员目前**只能被自动确立、无法转移**（`role` 单字段、无转移入口）。D2=a 把"建任务"锁给管理员 → **管理员账号一旦不可用（离职 / 换号 / 重装），IM 建任务会死锁且无补救路径**。

#### 3.5.1 EARS

| ID | 类型 | 句式 |

## 4. 量化口径（S2 必办三项 + 补充）

> 基线诚实原则：以下指标除标注外均为**新能力**，**基线 = 无**，首个观察窗建立基线。

### 4.1 观察窗口统一约定

| 项 | 约定 |
|---|---|
| 周窗口 | **7 个自然日**（与既有"本周概览"一致，非 now-7×24h） |
| 首次基线 | 各能力的**上线后首个完整周** |
| 归因 | 每项失败的**原因可分类**（权限 / 路径 / 系统错误） |

### 4.2 R1 —— IM 建任务成功率 / 回推到达率

| 指标 | 公式 | 分子 | 分母 | 目标 |
|---|---|---|---|---|
| IM 建任务成功率 | 成功创建数 ÷ 建任务请求数 | 返回创建成功的任务数 | 系统**解析为建任务意图**的消息数（含因权限 / 路径被拒的） | **≥ 95%** |
| 回推到达率 | 送达数 ÷ 应推送数 | `sender.Send` 无错的次数 | 应触发回推的事件数（每次进 waiting_input / 终态各计 1） | **≥ 99%** |

> **分母定义要点**：成功率的分母**必须含被拒的请求**，否则"拒绝一切"会让指标虚高到 100%。这与"指标必须能被做坏地优化"是同一类防线。

### 4.3 R3 —— Turn 分组覆盖率

| 指标 | 公式 | 目标 |
|---|---|---|
| Turn 分组覆盖率 | 被归入某个 Turn 分组的事件数 ÷ 任务总事件数 | **100%**（对**有 `TurnInfo`** 的任务） |

> **例外说明**：任务的首条 user 事件之前若存在系统事件，允许归入"Turn 0 / 起始"分组；无 `TurnInfo` 的旧任务不计入本指标（分母为 0 时展示"—"而非 0%，避免"看起来达标"）。

### 4.4 R6 —— 一次通过率（含数据起点）

| 项 | 定义 |
|---|---|
| 口径 | 无人工干预完成率 = 窗口内 `completed` 且 `Intervention` 记录数 **= 0** 的任务数 ÷ 窗口内 `completed` 任务数 |
| 数据源 | `Intervention` 持久化记录（**2.2.0 起落盘**） |
| **数据起点** | **只统计 2.2.0 上线时间之后创建的任务**；展示处标注起始日 |
| 基线 | 无（首周建立）；**不预设目标值** —— 先看真实分布再定 |
| 明确否决 | **不采用**"读 `Events` 里 `type=status`"的退化口径（事件保留上限会裁掉最旧事件 → 长任务被系统性误判为"没中断过"） |

### 4.5 R8 —— 统一率与三档视口

| 项 | 口径 |
|---|---|
| 输入控件统一率 | 使用 `components/ui/` 组件的控件数 ÷ 全站输入控件数 = **21 / 21** |

### ✅ S3 回报的需求层缺口（**CH-01 —— 已结清**）

R5-U1 原措辞要求「转移给同一渠道下另一台已绑定机器人的**绑定飞书账号**」，核实后不成立：

- `model.Bot` **无**绑定者账号字段，`larkreg` 设备流**不采集** open_id；
- 真正的权限源是 **`auth.Binding`（单账号，`Match(openid)`）**，`Bot.Role` 只管"哪台机器人受理特权命令"。

→ 「转移给另一台机器人的绑定账号」**在现有数据模型上无法表达**。

**裁决：D11 = d（复用 `Bind` 的替换语义）** —— 2026-09-12 用户确认。
依据：`BindingStore.Bind` 的注释（"Bind **replaces** any existing binding"）与实现（单指针 `s.cur = &b`）均为**替换语义** → **一次 bind 即原子转移**，无需新字段、无需设备流改动，且 `AC-R5-01/02` 原样成立。备选 **b**（加 `Bot.OwnerOpenID`，+1 人日）与 **c**（降级为重新绑定流程并降低 `AC-R5-02`）**均被否决** —— b 解决的是"机器人属于哪个账号"这个 d 路径根本不需要回答的问题；c 把一条**可判定的不变量**降级成"窗口内不可用"。
