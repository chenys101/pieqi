### 2.1 `Intervention` 落盘的存储位置（M3 的取舍）

**选择：挂进 `Task` 记录**（而非独立文件）。理由：
- 口径是「**该任务**是否被打断」→ 与 task 同生命周期，独立存储会引入"两处数据要同步"的第二来源；
- 仓库已有判据：**数据没有第二个来源，就不该有第二个算法** —— 独立存储后统计还需 join，正是分叉的温床。

⚠️ **代价（必须记住）**：`Task` 记录随之变大。`Intervention` 单条极小（`kind`/`source`/`created_at`），且次数受人工操作频次约束，可接受。

### 2.2 `IMSessionStore` 结构（M5）

```go
// 键 = channel + ":" + chatID + ":" + botID（PRD §3.1.1 定义）
type IMSession struct {
    Key         string    `json:"key"`
    ProjectPath string    `json:"project_path"` // 绝对路径
    UpdatedAt   time.Time `json:"updated_at"`
}
```

| 决策 | 结论 | 理由 |
|---|---|---|
| 键含 `botID` | ✅ 包含 | 一台机器人 = 一个 IM 身份；换机器人 = 换上下文，与既有模型一致 |
| 是否含 `senderID` | ❌ 不含 | PRD §3.1.1 已定为 `(channel + chatID + botID)`；且 D2=a 下建任务仅管理员 → 群内不会有第二人写入 |
| 落盘 / 内存 | **落盘** | 重启保留（S3-2 倾向）；内存态会让"选好项目后服务重启"前功尽弃 |
| 过期策略 | 无 TTL，`/项目` 覆盖 | 显式动作覆盖，不用隐式过期制造"昨天能用今天不能用"的困惑 |
| 损坏处理 | **返回 error，不静默重建** | 与 `NewBotStore` / `BindingStore` 同判据：不静默丢绑定，交由运维决定恢复还是重建 |

## 3. 接口契约

### 3.1 新增 / 变更端点

| 方法 | 路径 | 门禁 | 用途 | 归属 |
|---|---|---|---|---|
| `GET` | `/api/bots` | `ExternalAuth` | **响应改 `botDTO`**（`has_sys_prompt` + `sys_prompt_len`，无明文） | R2 |
| `POST` | `/api/bots` | `BindOpGate` | 请求体含 `sys_prompt`；**长度校验**；响应改 `botDTO` | R2 |
| `PATCH` | `/api/bots/:id` | `BindOpGate` | 同上（部分更新语义，见 §4.2） | R2 |
| `POST` | `/api/larkreg/config` | `BindOpGate` | 设备流落 bot 路径，**同一长度校验** | R2 |
| `GET` | `/api/bots/:id/prompt` | `BindOpGate` | **新增**：内网回显明文（编辑用） | R2 |
| `POST` | `/api/bots/:id/transfer-admin` | `BindOpGate` | **新增**：原子转移管理员，body `{target_bot_id}` | R5 |
| `GET` | `/api/tasks` | 现有 | **复用**：`projects` 分组即 R1 的项目白名单来源 | R1 |

### 3.2 关键响应体（`botDTO`，M6）

```json
{
  "id": "b_xxx", "channel": "lark", "name": "飞书 · 管理员",
  "role": "admin", "app_id": "cli_xxx", "created_at": "2026-09-12T10:00:00Z",
  "has_sys_prompt": true, "sys_prompt_len": 128
}
```

> ⚠️ **`botDTO` 不是可选优化，是 `C4` 的修法本体**：`model.Bot` **同时是 `index.json` 的落盘格式**（`bots_store.go` 写/读同一结构体）。若图省事给 `SysPrompt` 加 `json:"-"`，API 与磁盘**一起断** → 用户已存的提示词**重启后消失**，且症状像"偶发没存上"，极难归因。
> **一般化判据：`api` 与 `core` 共用 `model` 结构体时，"别让它出接口"这类需求，先确认这个结构体是不是同时也是落盘格式。**

### 3.3 IM 命令契约（R1）

| 用户输入 | 系统行为 | 失败回复 |
|---|---|---|
| `/项目 <名称>` | 白名单解析 → 记入会话 → 回复「项目名 + 绝对路径」 | 见 §4.1 三类失败 |
| `/项目`（无参） | 回复当前会话项目；未选定则给引导 | — |
| `/任务 <描述>` | 用当前项目**显式**建任务 | 未选项目 → 引导 |
| 裸文本 | 用当前项目**隐式**建任务（**D10 已定为"直接建"**） | 未选项目 → 引导，**不建任务、不调用模型** |
| `/帮助` | 命令清单 | — |

**命令优先级（必须显式固化，否则会与隧道命令打架）**：
`隧道命令（`隧道`/`续期`/`关隧道`…）` → `Pieqi 命令（`/项目`/`/任务`/`/帮助`）` → **裸文本建任务**。
> ⚠️ 隧道命令**不带 `/` 前缀**（「隧道」「续期 1h」），所以**必须"先判隧道、再判裸文本"**，否则「隧道」两字会被当成 prompt 去建任务 —— 直接破坏 AC-R1-05（回归）。

### 3.4 任务创建的公共出口（新抽函数）

```go
// core.CreateTaskFromRequest —— HTTP 与 IM 两条路径的**唯一**创建入口
type CreateTaskInput struct {
    ProjectPath   string
    Prompt        string
    Source        model.TaskSource   // http | im
    OriginChannel string
    OriginChatID  string
    OriginIdentity string
    OriginBotID   string
}
```

**为什么必须抽**：`api.createTask` 现在内含「TrimSpace → `filepath.Abs` → `os.Stat` 目录校验 → `deriveProjectID` → 预置 `Events[0]`（seq=1）→ `store.Create` → `runner.Start` → `GenerateTitleAsync`」一整串。
若 IM 路径**照抄一遍**，两处必然漂移（本仓库已踩过"各算各的"：列表数字与点开内容不同源）。
> **判据：同一语义动作有第二条调用路径时，必须先抽公共出口，再让两条路径都走它。**

## 4. 逐项方案（回答 S3-1 ~ S3-9）

### 4.1 R1 —— 路径校验细则 + 会话项目存储（S3-1 / S3-2）

#### ⚠️ 修正①：我的上一轮建议前提不成立

PRD §5 写"路径**必须在允许集合内**（S3 定细则）"，我在 S0–S1 建议的是"限定在 **PWA 已知项目集合**内"。
**核实后：该集合不存在。** `internal/api/tasks.go` 的 `createTask` 注释明写：

> 「项目不再预注册：一律用 `project_path`（绝对路径），`deriveProjectID` 派生稳定 id。」

前端项目列表来自 `GET /api/tasks` 响应的 `projects` 分组 —— 即**从任务历史派生的项目**，不是注册表。
**结论**：白名单来源改为 **任务历史派生的项目集合**（`project_path` 去重）。这**不改 AC 语义**（"允许集合"仍成立，只是集合来源变了），属 S3 职权内的细则确定，记为修正①。

| 项 | 结论 |
|---|---|
| **白名单来源** | `GET /api/tasks` 的 `projects` 分组中所有 `project_path`（去重、绝对路径） |
| **匹配键** | `deriveProjectID` 的 basename（目录名），**精确匹配**（非前缀、非模糊） |
| **0 个匹配** | 回复引导：含"请先在 PWA 建一次任务以登记该项目"+ `/帮助` |
| **≥2 个匹配** | ⚠️ **拒绝并要求更精确**，列出候选（`名称 @ 上级目录`）—— basename 会重名（`deriveProjectID` 只取最后一段），不能猜 |
| **1 个匹配** | 进入三道校验 |

**三道校验（缺一不可）**：

| # | 校验 | 失败回复 |
|---|---|---|
| 1 | **集合成员**：解析出的绝对路径 ∈ 白名单 | 「不在已知项目列表内」 |
| 2 | `os.Stat` 存在且是目录 | 「路径不存在或不是目录」 |
| 3 | **Git 仓库**：`.git` 存在且非 bare | 「不是 Git 仓库」 |

> **为什么"集合成员"这一条同时解决了越界问题**：白名单是**等值匹配**而非路径拼接，天然抗 `../` 穿越与符号链接越界 —— 攻击者无法通过构造输入得到集合外的路径。这是**用数据结构消除风险**，而不是用字符串清洗去追风险。
> **回复只回项目名与原因，不回系统路径细节**（`OriginIdentity` 是管理员，但仍不应把文件系统结构写进聊天记录 —— 聊天记录会被转发）。

#### 会话项目存储

见 §2.2。生命周期：落盘 → 重启保留 → `/项目` 覆盖 → 无 TTL。
**未选定时的行为（关键）**：回复引导，**不建任务、不调用模型**（R1-S1）。这条同时守住了"token 失控"的闸门。

### 4.2 R2 —— `C4` 修法 + 回显 + 长度上限（S3-3 / S3-4 / S3-5）

#### `C4` 修法（S3-5）

| 步骤 | 内容 |
|---|---|
| 1 | 新增 `api.botDTO`（§3.2），`listBots` / `createBot` / `updateBot` **三处响应统一**改用它 |
| 2 | ⚠️ **不改 `model.Bot` 的 json tag**（禁用 `json:"-"`，理由见 §3.2） |
| 3 | 请求侧保留明文输入（`createBotReq` / `BotPatch` 各自定义 `SysPrompt`） |
| 4 | **回归守门**：`AC-R2-06`（存 → 重启 → 仍在）必须逐次执行 —— 它专门守 `C4` 的陷阱 |

**PATCH 的部分更新语义（已核实，保持现状即可）**：`BotPatch.SysPrompt` 是 `*string`，`nil` = 未提供（不改），`""` = 显式清空（R2-U3b：空串视为"未设置"）。
> ⚠️ **不要把它改成值类型 `string`** —— 那样"只改名字"的请求会把提示词一并清空，且是静默的。`*T` 在这里不是风格偏好，是**区分"未提供"与"清空"的唯一手段**。

#### 回显方案（S3-3）

**结论：a —— 单开内网回显端点 `GET /api/bots/:id/prompt`（挂 `BindOpGate`）。**

| 通道 | 可见内容 |
|---|---|
| 外网可达（`ExternalAuth`：`GET /api/bots`） | `has_sys_prompt` + `sys_prompt_len`，**无明文** |
| 内网（`BindOpGate`：回显端点 / 写端点） | 明文 |

**为什么不是"UI 改成只可重设、不可查看"**：那会让管理员**无法增量打磨提示词**（改一个字要重写全文），而提示词恰恰是需要反复微调的配置项。
**为什么内网方案不造成体验缺口**：**写操作本来就是 `BindOpGate`（仅内网）** —— 机器人的配置 UI 实际只能在桌面/本机使用，手机端 `ExternalAuth` 路径本来就**只读**。回显与写的门禁保持一致，**零新增暴露面**。
> 若将来要让手机端也能编辑提示词，那是**先改"写只在内网"这个决策**，不在 2.2 范围（已列入 Non-goals 之外的显式说明）。

#### 长度上限（S3-4）

| 项 | 结论 |
|---|---|
| **数值** | **1000 rune**（对齐 PRD §3.2.1 R2-U3 的建议值） |
| **单位** | **rune 而非 byte** —— 1 rune = 1 个字符，中文用户按"字"计数；按 byte 则 1000 汉字会被算成 3000，写 300 字就报超限 |
| **校验位置** | ⚠️ **`BotStore.Create` / `BotStore.Patch` 内部（唯一出口）**，不是三个 handler 各写一遍 |
| **覆盖路径** | `POST /api/bots`、`PATCH /api/bots/:id`、`POST /api/larkreg/config` —— 三条路径**共享同一份校验** |
| **超限响应** | `{"error":"sys_prompt too long","length":1234,"limit":1000}` —— 含当前长度与上限（R2-U2b） |
| **空串语义** | 视为"未设置"（`has_sys_prompt == false`），不注入空段落（R2-U3b） |

> **判据**：**跨路径的一致性要求，只能靠"唯一出口"实现，不能靠"记得三处都改"。** PRD 的 `AC-R2-05` 明确要求逐条测三条路径 —— 就是在守这个。

### 4.3 R5 —— 管理员转移机制（S3-6）

#### ⚠️ 核实结果：管理员是**两层状态**，且**目标账号没有落点**

| 层 | 载体 | 作用 |
|---|---|---|
| **账号层** | `auth.Binding`（`cfg.Auth.FeishuBindingFile`，**单账号**） | `Match(openid)` —— **这才是真正的权限源** |
| **机器人层** | `Bot.Role == admin`（`BotStore.AdminBotID()`） | 哪台机器人**受理**特权命令 |

桥里的特权判定是**双条件**（`handleTunnelCommand`）：`adminBinding.Match(msg.UserID)` **且** `msg.BotID == adminBot.AdminBotID()`。

由此暴露两个硬事实：

1. ⚠️ **`Bot` 上没有"绑定者账号"字段，`larkreg` 设备流也不采集 open_id** → **"某台机器人属于哪个飞书账号"在数据层没有落点**。
2. ⚠️ **`BindingStore.Bind` 是"替换"语义** → 重新绑定第二个人会**覆盖**唯一账号：账号层换人了、机器人层没换 → 双条件判定失败 → 特权**静默失效**。

**结论：「管理员转移」在当前架构下没有原子路径。** 这也解释了 `bots_store.go` 里那句遗留注释（"管理员转移未建模，见此状态请显式 PATCH 另一台为 admin"）。

#### 我的方案

**(1) 触发方式：内网 PWA（`BindOpGate`），不做 IM 命令。**

| 理由 | 说明 |
|---|---|
| IM 命令**救不了它要解决的场景** | R5 的存在理由是"管理员账号不可用"；账号不可用时 IM 侧**恰好也失效**（`Match` 判不过）→ IM 通道对自己要解决的问题无能为力 |
| 跨两层状态的原子操作需要全局视图 | 转移要同时看"账号层"与"机器人层"，IM 文本交互无法承载 |
| 少一条 IM 特权路径 = 少一个攻击面 | 低频高权操作不值得开第二个入口 |

**(2) 目标人是否需在线确认：不需要，但必须两步 UI。**
内网访问本身即"对本机的控制权"证明（与 `BindingStore` 的安全注释同判据："bind/unbind MUST be gated to internal IPs"）。但 UI 必须是「选目标 → 二次确认」，且确认页**明示"当前管理员将失去什么"**（防误操作）。

**(3) 不加确认环节的代价必须说清**：被转者**不会收到通知**（他不知道自己是管理员了）。→ 方案里补一条：转移成功后**向新管理员的 IM 会话推送一条告知**（若其机器人已绑定且渠道可用；不可用则静默，UI 上提示"请线下告知"）。

**(4) 原子操作 + `Delete` 守门（这是本项的核心交付）**

| 变更 | 内容 |
|---|---|
| `BotStore.TransferAdmin(fromID, toID)` | **单次持锁内**同时改两个 bot 的 `role`，返回值唯一；不允许 admin 数变 0 |
| `POST /api/bots/:id/transfer-admin` | `BindOpGate`；body `{target_bot_id}` |
| ⚠️ **`Delete` 守门** | 现在删除 admin 机器人**不会**自动提升其他机器人（注释自证）→ **零管理员死锁口子**（正是 R5 要防的）→ 必须改为**拒绝删除唯一 admin**（除非先转移） |
| 校验 | 发起者非管理员拒绝（外挂 `Bindings.Match(调用者)`，R5-U3）；**目标 openid 缺失/格式非法拒绝**（R5-U4，D11=d 后的判据）；不允许 admin 数为 0（R5-U2） |

**(5) 两层同步（✅ CH-01 已结清 —— D11 = d）**

| 选项 | 做法 | 代价 | 能否满足 R5-U1 / AC-R5-02 |
|---|---|---|---|
| a | **只换 `Bot.Role`，不动 `auth.Binding`** | 0 | ❌ **不行** —— 权限源没换，特权仍归旧账号，转移是假的 |
| b | 加 `Bot.OwnerOpenID`（设备流采集绑定者）+ 转移时同步 `BindingStore.Bind(目标人的 Binding)` | +0.5–1 人日、+1 字段、设备流改动 | ✅ 可满足 —— **但已否决**（解决的是 d 不需要回答的问题） |
| c | 降级为"重新绑定"流程 | 0 新字段 | ⚠️ 部分 —— 有中间态窗口；**但已否决**（把可判定的不变量降级成"窗口内不可用"） |
| **d** ⭐ ✅ **已选** | **复用 `Bind` 的替换语义**（用户 2026-09-12 提出，经核实成立；**D11 裁决通过**）：新增 `TransferAdmin` 编排端点 = 校验调用者是当前管理员 → `Bindings.Bind(新账号)` **原子替换**（**不先 unbind**）→ 完成后可选 `PATCH` 换受理机器人 | **+0.3–0.5 人日**、**0 新字段**、**0 设备流改动** | ✅ `AC-R5-01` **原样**（替换原子，旧账号立即被拒）；✅ `AC-R5-02` **原样**（`cur` 单指针不可能有两个管理员，替换无零管理员窗口）；✅ `AC-R5-04 / R5-U1` 措辞已**走变更流程**（CH-01-Δ，见 PRD §8） |

> ✅ **已选定 d（D11，用户 2026-09-12 裁决）。依据：** `BindingStore.Bind` 的注释与实现均为**替换语义**（注释原文 "Bind replaces any existing binding"，实现是单指针 `s.cur = &b`）—— **它本身就是转移原语**。由此三点：
> - **不需要** `Bot.OwnerOpenID`（b）：该字段解决的是"某台机器人属于哪个账号"，而 d 的路径**根本不需要知道这件事**（目标是"谁来 bind"，openid 由操作者当场提供）；
> - **不能**先 `unbind`：`unbind → bind` 会制造**零管理员窗口**（正是 c 的病），而**直接 `bind` 是原子的**；
> - 与 c 的差别是本质的：c 把一个**可判定的不变量**降级成"窗口内不可用"，d **原样保住** `AC-R5-01/02`。
>
> ⚠️ **d 的唯一代价在 AC 措辞**：`AC-R5-04`（"目标不是已绑定账号 → 拒"）在 d 的语义下**不成立**（不再存在"已绑定/未绑定账号"之分），需改为"**目标 openid 缺失或格式非法 → 拒绝**"；`R5-U1` 的"另一台已绑定机器人的绑定飞书账号"限定需删（"哪台机器人受理"是独立可配项）。两项均**走变更流程并留痕**。
> ⚠️ **安全边界必须明示**：d 的边界 = **"能访问内网的人"**，与现状 `POST /api/auth/bind` **完全一致**（是承认现状，不是新增暴露面）；b 并不更严 —— 因为该端点本来就在（`api/binding.go:18`，仅内网）。
>
> ⚠️ **本轮同时核实（同构性）**：`unbind` 后的状态与"初始化未绑定"**严格同构** —— 初始态是 `feishu_binding.json` 不存在（`load()` 走 `os.IsNotExist` → `cur=nil`），解绑态是空文件（`load()` 走 `len(data)==0` → `cur=nil`），**两条路径落到同一个 `cur==nil`**，无需任何特判。**但这恰恰说明"解绑"这一步是多余且有害的**：既能直接 `bind` 原子替换，就不该引入零管理员窗口。
> ✅ **D11=d 已定，本节方案落地**：`AC-R5-04` 与 `R5-U1` 的措辞变更已按变更流程执行完毕（PRD §8 变更记录 **CH-01-Δ**，含工期/范围/已测作废量影响评估）。方案层**不再保留**"选 c 改 `AC-R5-02`"的备选。

### 4.4 R4 —— `sw.js` 版本注入（S3-7）

| 项 | 结论 |
|---|---|
| **方式** | **构建期替换**（不是运行期读取） |
| **机制** | Vite plugin（`apply: 'build'`）在 `writeBundle` 钩子里，把 `dist/sw.js` 中的占位符 `__SW_VERSION__` 替换为真实版本号 |
| **版本值** | `` `${pkg.version}-${Date.now().toString(36)}` `` |
| **缺失即失败** | plugin 在写回后**断言产物不含占位符**，仍含则 `throw` → 构建非 0 退出（AC-R4-03） |
| **策略不变** | `/assets/*` cache-first、HTML network-first（AC-R4-04） |

**为什么是构建期不是运行期**：

| 维度 | 构建期替换 | 运行期读取 |
|---|---|---|
| 时机 | `install` 时版本已确定，缓存名**立即可用** | 需先发一次请求拿版本 → **离线时拿不到 → 缓存不更新**（而离线可用正是 SW 的存在理由） |
| 失败模式 | 构建期暴露（可 fail） | 运行期静默 → 又变回 `v2` 那种"永不失效" |
| 依赖 | 无运行时依赖 | 新增一个网络调用 = 新增一个失败点 |

**两个必须避开的坑**：

1. ⚠️ **不能用 git short sha 作为版本值。** 本仓库的标准出包方式是 `git archive`，产出的**源码包不含 `.git`** → 对方机器上任何取 sha 的步骤都会失败。用 `package.json` version + 构建时间戳。
2. ⚠️ **不能用纯 `pkg.version`。** 同一版本多次构建会产出**相同**版本号 → `AC-R4-01`（两次构建版本号不同）不成立。必须叠加时间戳（ms 级 base36，同秒内两次构建的碰撞概率可忽略）。
3. **dev 模式**：`public/sw.js` 被原样服务，占位符不会被替换 → 建议 SW 注册处加 `import.meta.env.PROD` 守卫，**dev 不注册 SW**（避免占位符版本名被写入缓存）。⚠️ 这条会改动现有注册逻辑，须与既有 `_verify.mjs` 的真机基线比对（该脚本跑的是生产产物，理论上不受影响）。

### 4.5 R3 —— Turn 分组与反馈面板的联动状态（S3-8）

| 项 | 结论 |
|---|---|
| **放哪** | **Pinia store**（新增 `useTurnFocusStore`，或并入既有 session store） |
| **为什么不是页面 ref** | SPEC 要求"切页、切视口都保持"；本地 ref 在路由切回时**重置**（本仓库已在"变更反馈收起态"上踩过一次，判据相同） |
| **为什么不是 URL query** | 会污染历史记录、且与"切视口保持"无关；本项是**视图内联动**，不是可分享状态 |
| **state** | `{ byTask: Record<taskId, { turn: number \| null }> }` |
| **actions** | `focusTurn(taskId, turn)` / `clearTurn(taskId)` |
| **消费方** | Timeline（高亮 + 展开对应分组）与反馈面板（定位到该 Turn 的 diff）**读同一 state** |
| **数据同源（硬约束）** | Turn 的 diff **必须来自同一份 feedback bundle**（`GET /api/tasks/:id/feedback` 的 `turns[]`）；**禁止**在 Timeline 侧用第二个算法重算 |
| **旧任务** | 无 `TurnInfo` → `turn = null` → 单组平铺（R3-U3），不报错不白屏 |

> **判据（本仓库已付过学费）**：分组头部显示的文件数，**必须与点开后那份 diff 同源**。`AC-R3-02` 是"数字同源断言"，就是在守这条。数据没有第二个来源，就不该有第二个算法。

**增量更新（R3-S1）**：新事件到达时按 `StartEventSeq` 归属分组，**只追加**，不整块重排 —— 否则用户已展开的分组会被打断（`AC-R3-05`）。
